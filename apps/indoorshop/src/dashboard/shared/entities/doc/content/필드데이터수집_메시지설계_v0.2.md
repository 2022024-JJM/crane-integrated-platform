# 필드 데이터 수집 메시지 설계 v0.2 (조립/선행의장/선행도장)

현장 장비에서 OT Layer까지 오가는 필드 데이터 수집 설계(메시지 + 태그)입니다. 세 권역을 다룹니다.

- **조립/선행의장** — LiDAR 기반 형상인식 (리옵스). 장비 상태 + 실적률 결과 + 파이프라인 산출물
- **선행도장** — 제습기/가스히터 PLC에서 Modbus로 상태·운전 데이터 수집. 이 운전 데이터가 판별 서비스의 공정 추정 입력이 됨

기존 조립권역_메시지설계_v0.1.md의 A 채널을 장비 레벨까지 구체화한 버전입니다. v0.1 계열 문서(조립권역·센서디바이스상태·선행도장권역 메시지설계)는 레포 외부 자료이며, 본 문서가 해당 내용을 인라인으로 승계합니다.

## 수집 경로 — 두 가지 유형

권역별로 데이터가 ISL Engine에 도달하는 경로가 다르고, 그에 따라 설계 단위도 다릅니다.

- **메시지형 (조립/선행의장)** — 필드의 dockerized Java 서비스가 **MQTT Broker(EMQX)**에 JSON 메시지를 publish하고, **ISL MQTT Agent**가 이를 구독해 ISL Engine으로 전달합니다 (ASM-IF01, OUT-IF01). ISL에 저장되는 최종 형태는 태그형과 동일한 **태그ID/value**입니다 — 태그ID는 MQTT 토픽에서 유도되고, value에는 **JSON payload 통째가 1개 태그 값**으로 들어갑니다. 따라서 메시지 내부 구조(중첩 객체 포함)는 이 문서에서 자유롭게 설계할 수 있고, **토픽 설계가 곧 태그ID 설계**입니다. 수집은 ISL의 **선등록 모델**을 따릅니다 — 수집 대상 태그를 Engine에 먼저 등록하면 Agent가 그 목록을 받아 해당 토픽 구독을 시작하므로, 태그 ID는 사전에 정의·등록 가능해야 합니다(§태그 사전 등록과 프로비저닝). §1~§3이 이 유형입니다.
- **태그형 (선행도장)** — PLC가 Modbus로 **ISL Server의 도장 Modbus Agent에 직결**되며 MQTT Broker를 경유하지 않습니다 (PNT-IF01). Modbus Agent는 register를 주기 폴링해 **키-밸류 형식의 태그**로 수집하므로, 설계 단위는 JSON 메시지가 아니라 **태그(태그명 + 값)**입니다. 이쪽도 선등록 모델은 동일합니다 — 등록된 태그와 register map에 따라 폴링이 시작됩니다. §3-도장이 이 유형입니다.

> EMQX는 필드→OT 전달용 MQTT Broker이고, NATS는 ISL v4 내부 메시징 구현체입니다. 두 계층은 별개이므로 혼동하지 않습니다.

## 설계 원칙 — 설비·벤더·사업장 비종속

수집 체계는 ISL 기반 태그 중심입니다. 태그 네이밍과 메시지 스키마에 특정 장비 모델명(LIVOX AVIA, PTS-3050D 등)이나 벤더명(리옵스)이 들어가면, 장비 교체·벤더 변경·미국 필리조선소 확장 때마다 태그 체계를 다시 짜야 합니다. 그래서:

- 태그/메시지에는 **논리적 역할(role)**만 씁니다 — `lidar`, `pan_tilt`, `edge_pc`, `inference_ws`, `vision_ocr`, `plc_dehumidifier`, `plc_gas_heater`
- 실제 모델명/시리얼/벤더는 **장비 마스터(device registry)**에서 device_id로 조회하는 참조 데이터로 분리합니다
- 사업장/공장/설치위치도 태그 계층의 값으로만 존재하고, 스키마 구조 자체는 어느 사업장이든 동일합니다

즉 "거제 조립1공장의 LIVOX가 필리조선소의 다른 벤더 LiDAR로 바뀌어도" 태그 구조와 메시지 스키마는 그대로이고, device registry의 매핑만 바뀝니다.

## 식별 계층과 태그 네이밍 규칙 (제안)

권역 공통 식별 계층은 아래 7단계입니다.

```
{site}/{zone}/{shop}/{bay}/{device_role}/{device_id}/{metric}
```


| 세그먼트        | 의미                                    | 예                                                                                          |
| ----------- | ------------------------------------- | ------------------------------------------------------------------------------------------ |
| site        | 사업장                                   | geoje (향후 미국 필리조선소 등 확장 대비 (예: philly))                                                    |
| zone        | 권역                                    | assembly / outfitting / painting                                                           |
| shop        | 내업 shop (공장 단위. 도장은 도크 단위 — §3-도장 참조) | assembly1, outfitting1, dock1                                                              |
| bay         | shop 내 bay                            | bay3                                                                                       |
| device_role | 장비의 논리 역할                             | lidar / pan_tilt / edge_pc / inference_ws / vision_ocr / plc_dehumidifier / plc_gas_heater |
| device_id   | 장비 식별자 — device registry(§4)의 키와 동일   | LDR-GJ-A1B3-01                                                                             |
| metric      | 태그 항목                                 | operating_mode, actual_value, modbus_link 등                                                |


순번(device_seq: 01, 02) 대신 **device_id**를 쓰는 이유: 조립 ~210대·의장 ~140대 규모에서 bay별 순번 채번을 별도로 관리하면 충돌·중복 위험만 늘어납니다. device_id는 이미 전역 유일하고 registry 조인 키와 일치합니다. 장비 교체 시 태그명이 바뀌어 시계열이 나뉘는 점은 registry의 설치 위치 이력(installed_at/retired_at)으로 이어 붙입니다.

이 계층이 쓰이는 자리는 수집 유형에 따라 다릅니다.

- **태그형 (도장)** — 이 계층 전체가 곧 **태그명**입니다. 키-밸류 수집에서는 태그명이 유일한 식별 수단이므로 계층을 전부 태그명에 담습니다. 예: `geoje/painting/dock1/bay2/plc_gas_heater/PLC-GH-D1-03/actual_value`
- **메시지형 (조립/의장)** — site/zone/shop/bay 등은 **JSON payload의 필드**로 존재하고, 토픽(=태그ID)에는 태그 분리 단위까지만 담습니다 — 장비 상태는 장비별(device_id 포함), 실적·산출물은 shop/bay 작업 구역 단위 (아래 참조).

### MQTT 토픽 설계 — 메시지형 채널 (필드 서비스 → EMQX)

토픽이 곧 ISL 태그ID가 되므로, 토픽에는 **태그를 나누고 싶은 단위**까지만 담습니다.

```
ot/device/{zone}/{device_role}/{device_id}/status   ← §1 장비 상태 — 장비별 태그 (기존 센서디바이스_상태_메시지설계와 통합)
ot/sensor/{zone}/{shop}/{bay}/{stage}/actual        ← §2 실적률 결과 — 구역(shop/bay)×공정(stage)별 이벤트 스트림 태그
ot/pipeline/{zone}/{shop}/{bay}/artifact            ← §3 추론 과정 산출물 메타데이터 — 구역별 이벤트 스트림 태그 (신규)
```

- **장비 상태**는 토픽에 device_id를 넣어 **장비별 태그**로 분리합니다 — 조립 ~210대·의장 ~140대의 LiDAR를 장비별로 현재 상태 조회하고 장비 단위로 이력을 적재해야 하기 때문입니다. 토픽 하나에 전 장비 상태가 섞이면 ISL에서 장비별 조회가 안 됩니다.
- **실적률·산출물**은 특정 장비가 아니라 스캔 이벤트 단위이지만, **shop/bay 작업 구역 단위로 태그를 분리**합니다 — 구역별 이벤트 스트림이 독립 태그가 되어 구역 단위 조회·모니터링이 가능하고, 여러 구역의 이벤트가 태그 하나에 몰리지 않습니다. 장비 추적은 payload의 device_ids 필드로 합니다.
- scan_id·hull_no·block_id처럼 런타임에 무한히 생기는 식별자는 payload 전용입니다(선등록 불가). shop/bay는 태그 분리 단위로 토픽에 포함하되, payload 필드로도 유지합니다(토픽↔payload 정합 검증용).

인터페이스정의서 부록 A의 "운영 MQTT 토픽 명명 규칙: 미확정" 자리에 대응하는 확정 제안입니다. ISL 벤더(MQTT Agent 구독 설정)와 합의해 확정되면 인터페이스정의서에 반영합니다.

### NATS subject (참조 — ISL 내부)

ISL v4 내부에서 MQTT 토픽은 구분자만 바뀐 NATS subject로 1:1 변환됩니다 (`/` ↔ `.`). 예: `ot/device/assembly/lidar/LDR-GJ-A1B3-01/status` ↔ `ot.device.assembly.lidar.LDR-GJ-A1B3-01.status`. 이 변환은 ISL 스택(별도 repo) 소관이며, 필드 서비스가 publish하는 대상은 어디까지나 EMQX의 MQTT 토픽입니다.

### 태그 사전 등록과 프로비저닝

ISL의 수집 모델은 **선등록**입니다 — 수집할 태그를 Engine에 먼저 등록하고, Agent는 등록된 수집 대상 태그 목록을 Engine으로부터 받아 수집(MQTT 구독 / Modbus 폴링)을 시작합니다. 이 제약이 본 설계에 주는 귀결:

**정적 열거 가능성** — 태그 ID의 모든 세그먼트는 사전에 열거 가능한 값이어야 합니다: 유한 enum(zone, device_role, stage, metric)이거나 registry에 등록된 값(device_id). scan_id·hull_no·block_id처럼 런타임에 무한히 생기는 변량을 태그 ID에 넣지 않는 이유가 바로 이것이며, 이런 값은 payload 필드로만 다룹니다.

**이벤트 태그의 태그 ID는 레코드 키가 아니라 채널 주소** — 실적률·산출물은 레코드 하나하나가 유니크하지만, 그 유니크함을 태그 ID에 담으려 하면 안 됩니다. 레코드별 태그는 사전 등록이 불가능하고(무한 채번), 불필요합니다 — ISL은 LastValue 스냅샷 + 갱신 통지 전달자이지 레코드 저장소가 아니며, 채널 태그 하나로도 모든 레코드가 건별 Provider 호출로 후단(ISL DB Provider·판별 서비스)에 도달합니다(§태그 값의 수명). 키는 세 층으로 분리됩니다:

| 층 | 키 | 성격 | 보장 주체 |
|---|---|---|---|
| 채널 주소 | **태그 ID** (예: `ot/sensor/assembly/assembly1/bay3/arrangement/actual`) | 계측점 — 유한·정적, 선등록 대상 | ISL 태그 등록 |
| 레코드 유니크 키 | payload의 **idempotency_key** | 이벤트 건별 유일 | Hot Data DB 적재 시 unique 제약 |
| 도메인 조인 키 | payload의 scan_id / hull_no / block_id | 산출물↔실적 연결, 블록 추적 | 판별 서비스 / Hot Data DB |

따라서 실적률·산출물 채널에서 사전 등록할 태그 ID는 shop/bay 조합 × stage의 전개입니다. (stage↔zone 배정은 §2 stage enum 기준 — 공정 정의 확정 시 조정. 토픽/태그 세그먼트는 소문자, payload enum 값은 대문자 관례. shop/bay 목록은 현장 레이아웃 확정 후 열거 — 오픈 이슈)

| 채널 | 태그 ID 패턴 | 등록 수 |
|---|---|---|
| 실적률 (조립) | `ot/sensor/assembly/{shop}/{bay}/{stage}/actual` — stage: arrangement/processing/inspection/outbound | 조립 shop×bay 조합 × 4 |
| 실적률 (의장) | `ot/sensor/outfitting/{shop}/{bay}/{stage}/actual` — stage: wiring/penetration | 의장 shop×bay 조합 × 2 |
| 산출물 | `ot/pipeline/{zone}/{shop}/{bay}/artifact` | zone별 shop×bay 조합 × 1 |

예: `ot/sensor/assembly/assembly1/bay3/arrangement/actual`, `ot/pipeline/outfitting/outfitting1/bay2/artifact`

**태그 인벤토리 산정**


| 채널            | 태그 ID 패턴                                                          | 수량 산정                                                                                                              |
| ------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 장비 상태 (§1)    | `ot/device/{zone}/{device_role}/{device_id}/status`               | 장비 대수만큼 — LiDAR 조립 ~210대 + 의장 ~140대, 부속 장비(pan_tilt/edge_pc/inference_ws/vision_ocr)는 별도. **device registry에서 생성** |
| 실적률 (§2)      | `ot/sensor/{zone}/{shop}/{bay}/{stage}/actual`                    | shop×bay 조합 × stage (현장 레이아웃 확정 필요)                                                                               |
| 산출물 (§3)      | `ot/pipeline/{zone}/{shop}/{bay}/artifact`                        | shop×bay 조합 × 1                                                                                                    |
| 도장 운전 (§3-도장) | `{site}/painting/{dock}/{bay}/{device_role}/{device_id}/{metric}` | PLC 대수 × metric 6종                                                                                                 |


**프로비저닝 워크플로우** — 장비별 태그(상태·도장 운전)의 등록 원천은 device registry(§4)입니다.

1. 장비 신규 설치/교체 시 registry에 행 추가 (device_id 확정)
2. 그 행에서 파생되는 태그 ID를 ISL Engine에 등록
3. Agent가 갱신된 수집 대상 목록으로 수집 시작

**등록 전에는 필드 서비스가 publish해도 수집되지 않습니다.** 장비 설치 절차에 registry 등록 → ISL 태그 등록이 선행 단계로 들어가야 합니다.

### 태그 값의 수명 — LastValue와 이력 적재

ISL Engine은 태그당 **최신값(LastValue)만 유지**하고 시계열 이력을 쌓지 않습니다. 대신 **태그 값이 갱신될 때마다 Engine이 등록된 Provider들을 호출**합니다. 채널별 귀결:

- **장비 상태** — LastValue가 곧 현재 상태이므로 조회 용도로는 그 자체로 충분합니다. 상태 변화 이력·가동률 분석은 아래 적재 이력에서 합니다.
- **이벤트 태그(실적률·산출물)** — 연속 이벤트가 LastValue를 덮어써도 갱신 통지가 건마다 Provider로 나가므로 **이벤트가 유실되지 않습니다**. 중복 호출은 envelope의 idempotency_key로 걸러냅니다.
- **도장 운전 태그** — 공정 추정에 필요한 시계열은 ISL에 없으므로 아래 적재 경로로 구성합니다.

**이력 적재 주체는 ISL DB Provider(신규 설계)**입니다 — 적재 전용 Provider를 별도로 두어, Engine의 갱신 통지를 받아 **우리 DB 스키마에 맞게 경량 가공**(envelope 공통 필드 → 컬럼 매핑, payload 원본 보존)한 뒤 Hot Data DB(PostgreSQL)에 적재합니다. **zone 판별 서비스는 적재를 겸하지 않고 판별 전용**입니다 — Engine의 갱신 통지를 판별 입력으로 받고, 판별에 필요한 시계열·이력은 Hot Data DB에서 조회합니다. 역할 분담: **ISL 태그 = 현재 스냅샷, ISL DB Provider = 적재, Hot Data DB = 이력 소유, 판별 서비스 = 판별**. 이 문서의 "추이", "이력", "체인 조회" 서술은 모두 Hot Data DB에 적재된 이력을 전제합니다.

## 1. 장비 상태 메시지 — `ot/device/{zone}/{device_role}/{device_id}/status`

기존 센서디바이스_상태_메시지설계_v0.1.md의 공통 Envelope을 그대로 쓰되, device_type을 모델 기반이 아닌 역할 기반으로 바꾸고 역할별 raw_payload를 정의합니다. 도장 PLC는 MQTT를 경유하지 않으므로 이 메시지의 대상이 아닙니다 — 도장 설비의 통신 상태(modbus_link, fault_code)는 §3-도장의 태그로 수집합니다.

### 공통 (기존과 동일)

```json
{
  "device_id": "string",
  "device_role": "LIDAR | PAN_TILT | EDGE_PC | INFERENCE_WS | VISION_OCR",
  "site": "string",
  "zone": "ASSEMBLY | OUTFITTING",
  "shop": "string",
  "bay": "string",
  "status": "ONLINE | OFFLINE | ERROR | CALIBRATING",
  "last_heartbeat_at": "ISO8601",
  "error_code": "string | null",
  "occurred_at": "ISO8601",
  "ingested_at": "ISO8601",
  "idempotency_key": "string",
  "raw_payload": {}
}
```

### 역할별 raw_payload

**LIDAR** — 현재 LIVOX AVIA 단일 모델이나, 비종속 원칙에 따라 특정 모델에 종속되지 않는 항목만

```json
{ "scan_rate_pts_per_sec": "number", "temperature_c": "number", "connectivity_rssi": "number", "fov_mode": "string" }
```

**PAN_TILT**

```json
{ "pan_deg": "number", "tilt_deg": "number", "moving": "boolean", "preset_id": "string | null" }
```


| 필드                 | 설명                                             |
| ------------------ | ---------------------------------------------- |
| pan_deg / tilt_deg | 현재 자세 각도 — 스캔이 어느 방향을 보고 있었는지 실적 데이터와 대조할 때 필요 |
| moving             | 구동 중 여부 — 이동 중 스캔은 품질이 낮을 수 있어 구분              |
| preset_id          | 정반/구역별 사전 정의된 스캔 자세 프리셋 (있는 경우)                |


**EDGE_PC** (전처리 PC)

```json
{ "cpu_pct": "number", "mem_pct": "number", "disk_pct": "number", "queue_depth": "int" }
```

`queue_depth`는 전처리 대기 중인 스캔 건수 — 여기가 쌓이면 실적 반영이 늦어지고 있다는 신호입니다.

**INFERENCE_WS** (GPU 워크스테이션)

```json
{ "gpu_util_pct": "number", "gpu_mem_pct": "number", "gpu_temp_c": "number", "inference_queue_depth": "int", "model_version": "string" }
```

`model_version`은 추론 모델 버전 — 실적률 값이 갑자기 달라졌을 때 모델 교체 때문인지 추적하는 용도입니다.

**VISION_OCR** — 특정 조립공장 입구에만 설치

```json
{ "frame_rate_fps": "number", "ocr_confidence_avg": "number", "lens_condition": "CLEAN | DIRTY | OBSTRUCTED" }
```

## 2. 실적률 결과 메시지 — `ot/sensor/{zone}/{shop}/{bay}/{stage}/actual`

기존 조립권역_메시지설계_v0.1.md의 구조를 그대로 쓰되, 어느 장비 조합이 이 결과를 만들었는지 추적할 수 있게 필드를 보강합니다. (이전에 논의한 device_id 누락 문제를 여기서 해결) ISL MQTT Agent가 payload 통째를 1개 태그 값으로 수집하므로 device_ids·raw_payload 같은 중첩 객체를 그대로 쓸 수 있습니다. 레코드 건별 유니크함은 태그 ID가 아니라 payload의 idempotency_key가 대표합니다 (§이벤트 태그의 태그 ID 참조).

```json
  "source_system": "LiDAR Edge Service",
  "hull_no": "string",
  "block_id": "string",

  "scanned_at": "ISO8601",
  "device_ids": {
    "lidar": "string",
    "pan_tilt": "string | null",
    "edge_pc": "string",
    "inference_ws": "string",
    "vision_ocr": "string | null"
  },
  "event_type": "START | PROGRESS | COMPLETE",
  "occurred_at": "ISO8601",
  "ingested_at": "ISO8601",

    "reference_cad_id": "string",

```

| device_ids    | 이 결과를 만든 장비 체인 전체. 특정 LiDAR나 특정 모델 버전의 값만 이상할 때 역추적하는 용도. 벤더 비종속 원칙에 따라 역할 키로 구성 |

## 3. 파이프라인 산출물 메시지 — `ot/pipeline/{zone}/{shop}/{bay}/artifact` (신규)

실적률이 나오기까지의 중간 산출물 — 원본 PCD 정합본, Transformation Matrix, Segmentation 단위 PCD — 도 모니터링용으로 수집합니다.

### 큰 파일은 메시지에 싣지 않는다

PCD 파일은 수십 MB~GB 단위라 메시지·태그 파이프라인(EMQX → ISL)에 직접 실을 수 없습니다. 파일 본체는 **스토리지(로컬 blob 또는 파일서버)에 저장**하고, 메시지에는 **메타데이터 + 저장 위치 참조(URI)**만 싣습니다. 기존 아키텍처의 "Raw data(local blob) → PCD 학습서버" 흐름과 같은 원칙입니다. Transformation Matrix는 4×4 숫자 16개뿐이라 예외적으로 메시지에 직접 포함합니다.

```json
{
  "zone": "ASSEMBLY | OUTFITTING",
  "site": "string",
  "shop": "string",
  "bay": "string",
  "scan_id": "string",
  "artifact_type": "REGISTERED_PCD | TRANSFORMATION_MATRIX | SEGMENTED_PCD",
  "hull_no": "string | null",
  "block_id": "string | null",
  "segment_id": "string | null",
  "storage_uri": "string | null",
  "file_size_bytes": "number | null",
  "checksum": "string | null",
  "transformation_matrix": "number[16] | null",
  "produced_by_device_id": "string",
  "model_version": "string",
  "occurred_at": "ISO8601",
  "ingested_at": "ISO8601",
  "idempotency_key": "string",
  "raw_payload": {}
}
```


| 필드                    | 설명                                                      |
| --------------------- | ------------------------------------------------------- |
| scan_id               | 2번 실적 결과 메시지와 같은 스캔 회차 — 이 키로 "이 실적률이 어떤 PCD에서 나왔는지" 연결 |
| artifact_type         | 세 종류: 정합된 원본 PCD / 변환 행렬 / Segmentation 단위 PCD          |
| segment_id            | SEGMENTED_PCD일 때만 — 어느 세그먼트(부재/구역)인지                    |
| storage_uri           | 파일 본체 위치. TRANSFORMATION_MATRIX는 null                   |
| checksum              | 파일 무결성 검증용                                              |
| transformation_matrix | 변환 행렬은 4×4=16개 숫자라 메시지에 직접 포함. 나머지 타입은 null             |
| produced_by_device_id | 이 산출물을 만든 장비(주로 inference_ws)                           |


### 모니터링 활용

아래는 모두 Hot Data DB에 적재된 이력 기준입니다 (ISL 태그에는 최신 건만 남음 — §태그 값의 수명 참조).

- scan_id 하나로 "정합 PCD → 변환 행렬 → 세그먼트 PCD들 → 최종 실적률"의 전체 체인을 조회 가능
- 실적률이 이상할 때 해당 스캔의 PCD를 열어서 눈으로 확인하는 워크플로우 지원
- 세그먼트 개수/파일 크기 추이로 파이프라인 품질 변화 감지

## 3-도장. PLC 운전 데이터 태그 — Modbus Agent 수집 (신규)

선행도장은 LiDAR 같은 실적 이벤트가 아니라, 제습기/가스히터의 **연속 운전 데이터**를 주기 폴링으로 수집합니다. 이 원본 시계열이 판별 서비스의 공정 추정(전처리/도장 단계) 입력이 됩니다 — 추정 결과는 기존 선행도장권역_메시지설계의 실적 채널(`ot.sensor.painting.{stage}.actual`)로 나가고, 이 태그들은 그 재료인 원본입니다. ISL 태그에는 최신 폴링 값만 남으므로, 공정 추정용 시계열은 ISL DB Provider가 갱신 통지로 받은 값을 Hot Data DB에 적재해 구성하고, 판별 서비스는 그 이력을 조회합니다 (§태그 값의 수명 참조).

경로는 기존 아키텍처 그대로입니다: PLC → ISL Server의 도장 Modbus Agent 직결 (MQTT Broker 미경유, Kepware/OPC-UA 없음). Modbus Agent가 register를 폴링해 **키-밸류 태그**로 수집하므로, 설계 단위는 JSON 메시지가 아니라 태그입니다. 태그명은 §식별 계층의 슬래시 규칙을 따르고, metric별로 태그 1개씩 정의합니다.

### 태그 정의표

태그명: `{site}/painting/{dock}/{bay}/{device_role}/{device_id}/{metric}` (예: `geoje/painting/dock1/bay2/plc_gas_heater/PLC-GH-D1-03/actual_value`)


| metric                | 자료형                             | 단위                | 설명                                                |
| --------------------- | ------------------------------- | ----------------- | ------------------------------------------------- |
| operating_mode        | bool                            | -                 | 가동/정지 — 공정 추정의 핵심 신호                              |
| setpoint              | float                           | %RH(제습기) / °C(히터) | 설정값                                               |
| actual_value          | float                           | %RH(제습기) / °C(히터) | 실측값                                               |
| runtime_minutes_today | int                             | min               | 당일 누적 가동 시간 (PLC가 제공하는 경우) — 절대 공기 6~8일 패턴 대입에 유용 |
| modbus_link           | enum (OK / TIMEOUT / CRC_ERROR) | -                 | Modbus 통신 상태 — 조립/의장의 §1 상태 메시지에 해당하는 역할          |
| fault_code            | int (fault 없으면 0)               | -                 | 장비 fault 코드                                       |


- **단위는 별도 태그가 아니라 태그 정의의 고정 속성**입니다 — device_role별로 단위가 확정되므로(제습기=습도, 히터=온도) 값과 함께 흘려보낼 이유가 없습니다.
- 조립/의장 메시지의 envelope 필드(sampled_at/ingested_at/idempotency_key 등)는 태그 스트림에는 없습니다 — **폴링 시각은 태그 값에 붙는 타임스탬프**가 그 역할을 하고, 주기 폴링 시계열이라 idempotency 개념도 해당 없습니다.
- PLC 모델별 추가 register 값이 필요하면 metric을 추가로 정의합니다. Modbus register 주소는 태그명에 넣지 않습니다 — 아래 참조.

### Modbus register 비종속 원칙

register 주소(예: 40001)는 PLC 모델·결선에 종속된 물리 정보입니다. 태그/메시지에는 논리 필드명(operating_mode 등)만 쓰고, **register 주소 ↔ 논리 필드 매핑은 Modbus Agent의 설정(register map)으로 분리**합니다. 장비 교체 시 register map만 갱신하면 되고, 메시지 스키마와 그 뒤 파이프라인은 그대로입니다 — LiDAR 쪽 device registry와 같은 원칙입니다.

### 도장의 shop/bay 매핑

도장은 조립처럼 공장이 아니라 도크(1도크/2도크/느태/텍사코/GPS) 단위입니다. shop 자리에 도크를 매핑하는 것으로 제안합니다 (예: `geoje/painting/dock1/bay2/plc_gas_heater/PLC-GH-D1-03/...`). 도크 내부가 bay 개념으로 나뉘는지, 셀·구역 등 다른 명칭인지는 현장 확인 필요.

## scan_id 채번 규칙

채번 주체는 Edge PC(리옵스 스코프)입니다. 스캔이 발생하는 지점에서 ID가 생성돼야 이후 파이프라인 산출물 전체가 같은 키를 물고 갈 수 있습니다.

**형식은 지정하지 않습니다.** 내부 구조를 우리가 정하면 그걸 파싱하는 코드가 생기고, 벤더/채번 방식이 바뀔 때 같이 깨집니다. shop/bay/시각 같은 정보는 이미 메시지에 별도 필드로 있으므로 scan_id에 중복해 넣을 이유도 없습니다. 대신 리옵스와의 인터페이스 계약으로 아래 세 조건만 요구합니다.

1. **전역 유일성** — 전 사업장·전 장비에 걸쳐 중복 없음 (UUID 권장이지만 강제 아님)
2. **불변성** — 한 스캔에서 나온 모든 산출물(정합 PCD, 변환 행렬, 세그먼트, 실적률)에 동일 값
3. **불투명 취급** — 우리 쪽에서는 파싱하지 않고 조인 키로만 사용. 리옵스 내부 구조는 자유

## 4. 장비 마스터 (Device Registry) — 메시지가 아니라 참조 테이블

벤더 비종속 원칙의 반대편 짝이자, **ISL 태그 등록의 원천**입니다. 메시지에서 뺀 모델명/벤더/시리얼을 여기서 관리하고, 장비별 태그(§1 상태, §3-도장 운전)의 태그 ID가 registry 행에서 파생됩니다 (§태그 사전 등록과 프로비저닝).


| 필드                        | 예                                   |
| ------------------------- | ----------------------------------- |
| device_id                 | LDR-GJ-A1B3-01                      |
| device_role               | LIDAR                               |
| site / zone / shop / bay  | geoje / ASSEMBLY / assembly1 / bay3 |
| vendor                    | 리옵스 (조달 기준)                         |
| model                     | LIVOX AVIA (교체 시 여기만 갱신)            |
| serial_no                 | ...                                 |
| installed_at / retired_at | 설치/철거 일자                            |


장비를 교체하면 registry에 새 행을 추가하고 이전 행을 retire 처리 — 태그/메시지 스키마는 건드리지 않습니다. Hot Data DB에 `ot_device_registry` 테이블로 추가하면 됩니다(기존 ot_device_status와 device_id로 연결).

## 오픈 이슈

- LiDAR는 LIVOX AVIA 단일 모델 — §1 LIDAR raw_payload 항목(scan_rate, temperature, rssi, fov_mode)이 AVIA가 실제 제공하는 상태 항목과 일치하는지 리옵스/장비사 스펙 확인 필요. 모델 특화 항목은 raw_payload 추가 필드로 허용(향후 모델 교체·추가 대비)
