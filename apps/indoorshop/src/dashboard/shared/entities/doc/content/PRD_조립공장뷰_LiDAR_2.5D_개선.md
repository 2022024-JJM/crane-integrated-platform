# PRD — 조립 공장뷰 LiDAR 상태 및 2.5D 공간 UX 개선

- 문서 상태: Draft — **FR-2 ~ FR-7 구현 완료 반영 (2026-08-26)**, FR-1·FR-8·FR-9 미착수
- 대상 앱: `web-dashboard`
- 대상 모듈: `web-dashboard/src/processes/assembly`
- 기준 문서: `docs/필드데이터수집_메시지설계_v0.2.md`
- 작성 목적: 조립 공장/베이 모니터링 화면에서 LiDAR 상태, 공간 배치, 공정 선택 결과를 더 빠르고 직관적으로 파악하게 한다.

## 1. 배경

현재 조립 화면은 공장 목록, 공장 전체 3D 장면, 베이 상세 장면, LiDAR 상태, 인식 블록 상세를 제공한다. 그러나 현장 사용자가 화면을 처음 보았을 때 다음 질문에 즉시 답하기 어렵다.

1. 어느 베이에 문제가 있는가?
2. LiDAR가 단순 연결 상태인지, 보정 중인지, 품질이 저하된 상태인지?
3. 선택한 공정/베이가 전체 공장 안에서 어디에 있는가?
4. 같은 공정의 다른 대상과 선택 대상을 어떻게 구분하는가?
5. 3D 장면을 확대·축소·스크롤할 때 현재 시점과 조작 범위를 예측할 수 있는가?

필드 데이터 설계 v0.2는 조립 LiDAR 상태를 `ONLINE | OFFLINE | ERROR | CALIBRATING`으로 정의하며, 상태 메시지에 `last_heartbeat_at`, `error_code`, `scan_rate_pts_per_sec`, `temperature_c`, `connectivity_rssi`, `fov_mode`를 포함한다. 실적 이벤트는 베이와 공정 단계별로 `START | PROGRESS | COMPLETE`를 제공한다. 개선 화면은 이 계약을 기준으로 상태 표현을 확장한다.

## 2. 목표

- 사용자가 공장뷰 진입 후 3초 이내에 이상 베이와 이상 LiDAR의 존재를 인지한다.
- 공장 전체에서 각 베이의 경계, 이름, 점유/공정 상태를 한눈에 구분한다.
- 선택 대상은 강하게, 동일하거나 유사한 공정 대상은 약하게, 무관한 대상은 중립적으로 표현한다.
- 과도한 원근 왜곡 없이 공간감이 느껴지는 2.5D 기본 시점을 제공한다.
- 마우스 휠, 트랙패드, 드래그, 터치 조작이 페이지 스크롤과 충돌하지 않게 한다.
- 상세 카드의 정보 위계를 정리하되, 확정되지 않은 업무 데이터는 새로 추정하지 않는다.
- 한글과 영문, 숫자/장비 코드를 함께 표시해도 읽기 좋은 타이포그래피를 적용한다.

## 3. 비목표

- 실제 shop/bay 배치도와 좌표를 임의로 확정하지 않는다.
- LiDAR 메시지 스키마나 MQTT 토픽을 이 작업에서 변경하지 않는다.
- PCD 파일 뷰어, 추론 알고리즘 또는 실적 판별 로직을 변경하지 않는다.
- 미확정 Provider/결과 전달 프로토콜을 구현하지 않는다.
- 조립 모듈 개선을 위해 다른 공정 모듈을 직접 import하지 않는다.
- 전체 앱 디자인 시스템을 일괄 교체하지 않는다.

## 4. 사용자와 핵심 시나리오

### 4.1 주요 사용자

- 현장 운영자: 공장과 베이의 현재 가동/이상 상태를 빠르게 확인한다.
- 설비 담당자: 이상 LiDAR의 위치, 오류, 마지막 통신, 진단값을 확인한다.
- 생산 관리자: 베이별 현재 공정과 진행 상태를 비교한다.

### 4.2 핵심 시나리오

1. 사용자가 공장뷰에 진입하면 전체 베이 경계와 상태 요약이 2.5D 장면에 표시된다.
2. 오류/오프라인 LiDAR가 있는 베이는 색과 아이콘, 텍스트로 즉시 식별된다.
3. 사용자가 특정 베이 또는 공정 대상을 클릭하면 해당 대상은 강하게 강조되고, 동일 공정 대상은 낮은 강도로 문맥을 유지한다.
4. 상세 카드에서 핵심 상태를 먼저 보고, 필요할 때 LiDAR 진단값과 식별 정보를 펼쳐 본다.
5. 사용자는 휠/트랙패드로 자연스럽게 확대·축소하고, 장면 경계에서는 페이지 스크롤을 계속할 수 있다.

## 5. 정보 구조

공장뷰는 세 단계로 정보를 제공한다.

| 단계 | 기본 표시 | 목적 |
|---|---|---|
| 공장 요약 | 전체 상태, 이상 베이 수, LiDAR 온라인 수, 데이터 최신 시각 | 공장 전체 이상 유무 판단 |
| 2.5D 맵 | 베이 경계/라벨, 점유, 공정, LiDAR 상태, 선택 강조 | 위치와 상태의 결합 인지 |
| 상세 카드 | 선택 대상 상태, 공정/블록 요약, LiDAR 진단, 최근 이벤트 | 원인 확인과 다음 행동 판단 |

맵과 상세 카드는 동일한 `selectedBayId` 및 선택 공정 상태를 사용한다. 한쪽에서 선택하면 다른 쪽도 즉시 동기화한다.

## 6. 기능 요구사항

### FR-1. LiDAR 상태 표현 확장

화면의 LiDAR 기본 상태는 기준 문서와 동일한 네 종류를 지원한다.

| 원본 상태 | 사용자 표시 | 시각 표현 | 우선순위 |
|---|---|---|---|
| `ONLINE` | 정상 | 녹색 상태점 + 정상 아이콘 | 4 |
| `CALIBRATING` | 보정 중 | 파란색 상태점 + 완만한 회전/호흡 애니메이션 | 3 |
| `OFFLINE` | 연결 끊김 | 회색 상태점 + 연결 끊김 아이콘 | 2 |
| `ERROR` | 오류 | 적색 상태점 + 경고 아이콘 | 1 |

- 색만으로 상태를 전달하지 않고 아이콘과 상태 텍스트를 함께 표시한다.
- 여러 LiDAR를 요약할 때 베이 대표 상태는 가장 높은 위험 상태를 사용한다: `ERROR > OFFLINE > CALIBRATING > ONLINE`.
- `last_heartbeat_at`을 기준으로 데이터 신선도를 표시한다. 임계값은 운영 합의 전까지 설정값으로 분리하며 UI 코드에 하드코딩하지 않는다.
- `error_code`가 있으면 상세 카드에 표시하되 사용자용 오류 설명 매핑이 없을 때 원문 코드를 그대로 보존한다.
- LiDAR 상세에는 제공된 값만 표시한다: 스캔율, 온도, RSSI, FOV 모드. 값이 없으면 `-`로 표시하고 정상값을 추정하지 않는다.
- 온도/RSSI/스캔율의 정상·주의·위험 임계값은 장비사 확인 전 색상 판정을 하지 않고 수치만 표시한다.
- 축약 요약은 `정상 7 · 보정 1 · 오류 1`처럼 상태별 대수를 제공한다.

### FR-2. 공장/베이 상태의 직관적 표현

> **상태: 구현 완료 (2026-08-26).** 베이 바닥 면(`floors`)·외곽선·상태 라벨(`createBayStatusLabel` — 베이명·대표 상태점+텍스트·`작업 중 n건`/`작업 없음`/`데이터 미수신`)을 구현했다. 대표 상태는 `bayStatusSummary.worstSensorStatus`(ERROR > OFFLINE > ONLINE — `calibrating` 은 FR-1 미착수로 모델에 없음), 상태별 대수 요약은 라벨 title 로 제공한다. 이상 베이는 바닥 상태 오버레이 + 라벨 링으로 공정 강조보다 우선해 식별된다. 실적 이벤트(START/PROGRESS/COMPLETE) 문구와 진행률 표시는 프론트 모델에 `event_type`/`block_progress_rate` 계약이 아직 없어(§7.2 연동 전) 표시하지 않았다 — 임의 계산·추정 없음 원칙 준수.

- 각 베이는 바닥 면, 외곽선, 베이명 라벨로 명확히 분리한다.
- 베이 라벨은 최소한 베이명, 대표 상태, 현재 공정 또는 `작업 없음`을 표시한다.
- 베이 상태는 다음 신호를 결합해 보여주되 각각의 원본 상태를 숨기지 않는다.
  - LiDAR 상태: FR-1의 최악 상태
  - 점유 상태: 블록 있음/없음
  - 실적 이벤트: `START`, `PROGRESS`, `COMPLETE`
  - 데이터 신선도: 마지막 heartbeat 또는 scan 시각
- 공정 진행 상태는 다음 사용자 문구로 표시한다.

| 이벤트 | 사용자 표시 | 권장 표현 |
|---|---|---|
| `START` | 작업 시작 | 얇은 진행 띠와 시작 아이콘 |
| `PROGRESS` | 작업 중 | 진행률이 있으면 수치/바, 없으면 `작업 중` |
| `COMPLETE` | 완료 | 완료 체크와 완료 톤 |
| 이벤트 없음 | 작업 없음/미수신 | 중립 톤, 두 상태를 데이터 유무에 따라 구분 |

- `raw_payload.block_progress_rate`가 있을 때만 진행률을 표시한다. 없으면 임의 계산하지 않는다.
- 알람/오류 상태는 공정 색상보다 우선해 식별 가능해야 한다.

### FR-3. 베이 단위 상세 맵

> **상태: 구현 완료 (2026-08-26).** 배치 계약 `FactoryLayout`/`BayLayout`(`api/bayLayout.ts` — bayId·표시명·중심/크기/방향)과 mock adapter(`buildMockFactoryLayout`, `source: 'mock'` 으로 목업임을 데이터 수준에서 구분, 열당 4면 + 통로 배치)를 두고 `fetchFactoryLayout` 으로 내려준다. 뷰어는 좌표를 받아 그릴 뿐 배치를 하드코딩하지 않는다. 레이어 5종(바닥·경계/라벨/블록·점군/라이다/상태 오버레이)을 뷰어의 `레이어` 패널에서 독립 제어한다. 라벨 겹침은 이상 라벨 z-index 우선 + 밀집(6면 초과) 시 정상 베이 라벨 축약으로 처리한다.

- 공장 전체 장면에 모든 베이의 실제 경계와 통로 관계를 표시할 수 있어야 한다.
- 베이별로 다음 레이어를 독립 제어할 수 있어야 한다.
  - 바닥/경계
  - 베이명 라벨
  - 블록/작업 대상
  - LiDAR 위치와 시야 방향
  - 상태 오버레이
- 밀집 구간에서 라벨이 겹치면 선택 대상과 이상 상태 라벨을 우선하고 나머지는 축약/숨김 처리한다.
- 실제 shop/bay 좌표는 현장 레이아웃 확정 후 데이터로 주입한다. 그 전 목업은 `mock`임을 개발 데이터 수준에서 명확히 구분한다.
- 레이아웃 데이터는 최소 `bayId`, 표시명, 외곽 다각형 또는 크기/중심 좌표, 방향, 소속 shop을 포함한다.
- 베이 형상과 배치는 `processes/assembly` 내부 데이터/API 계층에서 관리하고 뷰어 컴포넌트에 하드코딩하지 않는다.

### FR-4. 2.5D 기본 시점과 공간감

> **상태: 구현 완료 (2026-08-26).** 기본 시점 = 고도 52°·방위 18° 의 비스듬한 부감 + 좁은 화각 36°(정사영 대신 낮은 원근 채택 — 원거리 베이 축소 억제). 바닥 판을 0.5m 돌출시켜 깊이를 표현하고, 장식 애니메이션·안개·반사는 쓰지 않는다. `전체 맞춤`/`선택 정반 맞춤`/`기본 시점` 버튼(부드러운 전환, `cameraTween`)과 축 기즈모(기존)를 제공한다. 저사양 모드는 도움말 패널의 스위치(`qualityMode`, localStorage 유지)로 픽셀 밀도를 낮춘다 — 임계 자동 판별은 단말 사양 확정(오픈 이슈 7) 후.

- 기본 공장뷰는 위에서 비스듬히 내려다보는 2.5D 시점으로 제공한다.
- 정사영 또는 낮은 원근감을 기본으로 사용해 원거리 베이가 과도하게 작아지지 않게 한다.
- 바닥 높이, 베이 경계 돌출, 부드러운 그림자/접지 음영으로 깊이를 표현한다.
- 상태 판독을 방해하는 과도한 반사, 안개, 장식 애니메이션은 사용하지 않는다.
- `전체 맞춤`, `선택 베이 맞춤`, `기본 시점 복원` 동작을 제공한다.
- 현재 장면의 방향을 알 수 있도록 축/방향 표시를 유지한다.
- 저사양 환경에서는 그림자와 후처리를 낮추거나 끌 수 있어야 한다.

### FR-5. 선택 및 유사 공정 강조

> **상태: 구현 완료 (2026-08-26).** 강조 규칙은 `bayEmphasis.ts` — 선택 100% / 동일 stage 55% / 무관 15%(라벨은 38%로 상호작용 유지). 유사 공정 그룹 확정 전이므로 `동일 stage(송선 현공정 코드)만 유사 대상` 규칙을 적용했다(`bayStatusSummary.bayStage`, 최빈값·정합 실패 제외). 라벨 클릭 = 지속 선택(카메라 자동 맞춤), 선택된 라벨 재클릭 = 정반 화면 진입, hover = 임시 강조(기존 탭 연동 유지), 빈 공간 클릭·`Esc` = 해제. 라벨은 `<button>` 이라 키보드 선택 가능. 선택 상태의 URL 반영은 후속 기술 설계 결정 대기 — 현재는 로컬 state 라 뒤로가기를 방해하지 않는다. 단위 테스트: `bayEmphasis.test.ts`, `bayStatusSummary.test.ts`.

사용자가 베이, 블록 또는 공정 항목을 클릭하면 다음 강조 규칙을 적용한다.

| 대상 | 불투명도/명도 기준 | 추가 표현 |
|---|---:|---|
| 직접 선택 대상 | 100% | 굵은 외곽선, 명확한 라벨, 상세 카드 연결 |
| 동일 공정 단계 대상 | 45~60% | 동일 계열 색, 얇은 외곽선 |
| 같은 공정군의 유사 단계 | 25~40% | 저채도 동일 계열 색 |
| 무관한 대상 | 10~20% | 중립색, 상호작용 가능한 형태는 유지 |

- `유사 공정`은 이름 유사도가 아니라 명시적인 공정 그룹 설정으로 판단한다.
- 조립의 공정 단계는 기준 문서의 `ARRANGEMENT`, `PROCESSING`, `INSPECTION`, `OUTBOUND`를 사용한다.
- 유사 공정 그룹 정의가 확정되기 전에는 `동일 stage만 유사 대상`으로 처리한다.
- 선택 해제는 빈 공간 클릭 또는 `Esc`로 가능해야 한다.
- 마우스 hover는 임시 강조, click은 지속 선택으로 구분한다.
- 선택 상태를 URL에 반영할지는 후속 기술 설계에서 결정하되, 브라우저 뒤로가기를 방해해서는 안 된다.

### FR-6. 자연스러운 3D 조작과 스크롤

> **상태: 구현 완료 (2026-08-26).** 좌클릭 회전 / 우클릭·Shift+드래그 이동 / 휠 줌으로 통일하고 도움말(`ViewportHelp`)을 그 순서로 다시 썼다. 조작 포커스(`viewportInput.bindViewportFocus`): 클릭 전에는 휠을 소비하지 않고(안내 칩 표시), 포커스 중에도 줌 한계에서는 페이지 스크롤로 이어진다. `Esc`·뷰포트 밖 클릭으로 포커스 해제. 카메라 한계: 최소/최대 거리(장면 크기 비례)·수직 회전 10~78°·이동 경계 클램프(`clampPanToBounds`). 감쇠는 OrbitControls damping, `prefers-reduced-motion` 이면 카메라 전환을 생략하고 즉시 이동한다(`cameraTween`). 실측 뷰어(RealScanViewer)에도 같은 포커스 규칙을 적용했다. 트랙패드 pinch/모바일 제스처 세분화는 OrbitControls 기본 동작 수준 — 현장 단말 확정 후 검증 항목.

- 데스크톱 기본 조작은 좌클릭 회전, 우클릭/Shift+드래그 이동, 휠 확대·축소로 통일하고 도움말에 표시한다.
- 트랙패드 pinch/두 손가락 스크롤을 구분해 급격한 확대나 이동이 발생하지 않게 한다.
- 줌 속도는 입력량에 비례하고 감쇠(damping)를 적용해 갑자기 멈추거나 튀지 않게 한다.
- 카메라의 최소/최대 거리, 수직 회전 범위, 이동 가능한 공장 경계를 제한해 장면 이탈을 방지한다.
- 뷰포트가 조작 포커스를 가진 동안만 3D 입력을 소비한다. 사용자가 장면의 줌 한계에서 계속 스크롤하면 페이지 스크롤로 자연스럽게 이어져야 한다.
- `Esc` 또는 뷰포트 밖 클릭으로 조작 포커스를 해제할 수 있어야 한다.
- 모바일에서는 한 손가락 회전, 두 손가락 이동/확대 규칙을 제공하고 브라우저 기본 제스처를 불필요하게 막지 않는다.
- `prefers-reduced-motion`에서는 카메라 전환과 상태 애니메이션 시간을 줄이거나 제거한다.

### FR-7. 타이포그래피 개선

> **상태: 구현 완료 (2026-08-26).** `Pretendard Variable`·`IBM Plex Mono` 는 npm 로컬 번들(main.tsx import — CDN 비의존)로 이미 로드되고 있고 시스템 sans 폴백이 토큰에 있음을 확인했다. 크기/굵기/행간 토큰(`--text-*`, `--app-font-scale`)은 기존 체계를 유지하며 새 라벨도 그 토큰만 쓴다. 3D 위 라벨은 어두운 유리 패널 위 고대비 글자 + 베이명 truncate(글자 수 제한)로 새로 구성했고, 정반코드·건수 등 수치에는 `tabular-nums` 를 적용해 갱신 시 폭이 흔들리지 않는다. 100%/125% 글자 배율·Windows Chromium 검수는 수동 확인 항목으로 남는다(기존 `--app-font-scale` 배율 체계가 라벨에도 그대로 적용됨).

- 한글 UI 기본 서체는 현재 토큰에 정의된 `Pretendard Variable`을 실제로 로드하고, 로드 실패 시 시스템 sans-serif로 폴백한다.
- 영문/숫자 코드에는 현재 `IBM Plex Mono`를 유지하되, 장문 설명에는 사용하지 않는다.
- 화면 제목, 베이명, 상태, 보조 정보의 크기/굵기/행간을 토큰으로 통일한다.
- 3D 위 라벨에는 본문보다 높은 대비와 제한된 글자 수를 적용한다.
- 장비 ID, 시각, 수치는 tabular number를 사용해 값 갱신 시 폭이 흔들리지 않게 한다.
- 외부 CDN 폰트에만 의존하지 않는다. 운영망 제약을 고려해 라이선스 검토 후 로컬 번들 또는 사내 배포 경로를 사용한다.
- 글꼴 변경 후 한글/영문 혼용, 100%/125% 글자 배율, Windows Chromium 환경을 검수한다.

### FR-8. 상세 카드 재구성

상세 내용 자체는 확정 전이므로, 카드의 구조와 우선순위만 먼저 정의한다.

1. 헤더: 베이명, 대표 상태, 마지막 갱신 시각
2. 핵심 요약: 현재 공정, 블록 식별값, 진행 상태
3. LiDAR 요약: 상태별 대수와 이상 장비 우선 목록
4. 펼침 영역: 장비 ID, heartbeat, 오류 코드, 스캔율, 온도, RSSI, FOV
5. 보조 액션: 선택 베이 맞춤, 상세 화면 이동

- 이상 장비와 최근 변경 정보를 정상 장비보다 위에 둔다.
- 카드 선택과 맵 선택을 양방향 동기화한다.
- 값이 없는 항목은 카드 공간을 크게 차지하지 않게 축약한다.
- 실데이터 계약이 없는 새로운 KPI, 예측치, 가동률은 추가하지 않는다.
- 카드 전체를 클릭 가능하게 만들 경우 내부 버튼과의 중첩 클릭/키보드 포커스를 방지한다.

### FR-9. 추가 개선 제안

- 상태 범례는 항상 현재 화면에서 사용 중인 색/아이콘만 표시한다.
- `이상만 보기`, `미점유 숨기기`, 공정 단계 필터를 제공한다.
- 이상 베이가 화면 밖에 있으면 가장 가까운 화면 가장자리에 방향 표식을 제공한다.
- 데이터 수신이 끊긴 경우 마지막 값을 정상처럼 보이지 않게 전체 뷰에 `데이터 지연` 상태를 표시한다.
- 첫 진입 시 간단한 조작 힌트를 한 번 제공하고 이후 도움말에서 다시 볼 수 있게 한다.
- 로딩 중 이전 장면을 유지하되, 이전 데이터임을 반투명 오버레이와 시각으로 알린다.

## 7. 데이터 요구사항과 매핑

### 7.1 LiDAR 상태 입력

출처 토픽: `ot/device/{zone}/{device_role}/{device_id}/status`

| UI 필드 | 메시지 필드 | 필수 여부 | 비고 |
|---|---|---|---|
| 장비 식별 | `device_id` | 필수 | registry 조인 키 |
| 장비 역할 | `device_role` | 필수 | 이 화면은 우선 `LIDAR`만 대상 |
| 위치 | `site`, `zone`, `shop`, `bay` | 필수 | 토픽과 payload 정합 검증 필요 |
| 상태 | `status` | 필수 | 4종 enum |
| 마지막 통신 | `last_heartbeat_at` | 필수 | ISO8601 |
| 오류 | `error_code` | 선택 | 없으면 숨김 또는 `-` |
| 진단 | `raw_payload.*` | 선택 | 값 존재 시만 표시 |

현재 프론트 모델의 `online | offline | error`에는 `calibrating`과 진단 필드가 없다. 구현 시 타입과 fixture/API 매핑을 함께 확장해야 한다.

### 7.2 공정/실적 입력

출처 토픽: `ot/sensor/{zone}/{shop}/{bay}/{stage}/actual`

- 베이 식별: `shop`, `bay`
- 공정 단계: `stage`
- 이벤트 상태: `event_type`
- 작업 식별: `hull_no`, `block_id`, `scan_id`
- 진행률: `raw_payload.block_progress_rate`가 있을 때만 사용
- 최신성: `occurred_at`, `ingested_at`

### 7.3 레이아웃 입력

필드 데이터 설계 문서에서 조립 shop/bay 목록과 현장 레이아웃은 오픈 이슈다. 따라서 개발 착수 전 아래 자료가 필요하다.

- 공장별 shop/bay 목록과 안정적인 ID
- 베이 외곽 또는 중심/폭/길이/방향 좌표
- 통로, 벽체, 주요 설비 중 화면에 필요한 항목
- LiDAR 설치 좌표와 방향
- 좌표계 원점, 축 방향, 단위

실제 자료가 없을 때는 현재 목업 좌표계를 사용할 수 있으나 운영 데이터로 간주하지 않는다.

## 8. 화면 상태와 예외 처리

- 로딩: 기존 장면이 있으면 유지하고 갱신 중임을 표시한다.
- 빈 데이터: `작업 없음`과 `데이터 미수신`을 구분한다.
- 부분 실패: 레이아웃은 표시하되 실패한 상태 레이어만 경고한다.
- 오래된 데이터: 마지막 수신 시각과 함께 지연 상태를 표시한다.
- 알 수 없는 enum: 화면을 깨뜨리지 않고 `알 수 없음`으로 표시하며 원본 값은 진단 로그에 보존한다.
- WebGL 미지원/실패: 베이 목록 기반 2D 대체 화면과 상세 카드 접근을 제공한다.

## 9. 접근성 요구사항

- 상태색은 WCAG AA 대비를 만족하고 텍스트/아이콘을 병행한다.
- 맵의 모든 선택 대상은 키보드로 순회 및 선택할 수 있어야 한다.
- 포커스 표시를 3D 오버레이와 상세 카드 모두에서 명확히 제공한다.
- 상태 변경은 필요 시 `aria-live="polite"` 요약 영역으로 알리되 잦은 센서 갱신을 모두 읽지 않는다.
- 캔버스만으로 정보를 독점하지 않고 동일 정보를 목록/상세 카드에서도 제공한다.

## 10. 성능 및 품질 요구사항

- 목표 환경에서 공장뷰 첫 유효 화면을 3초 이내 표시한다(네트워크 및 자산 기준은 기술 설계에서 고정).
- 일반 조작 중 30 FPS 미만이 지속되지 않도록 하고 목표는 60 FPS로 한다.
- 상태값 갱신은 전체 3D 장면 재생성 없이 해당 베이/장비 표현만 갱신한다.
- 화면 밖 라벨과 불필요한 장식은 렌더링을 줄인다.
- 공장 레이아웃과 무거운 3D 자산은 lazy load 원칙을 유지한다.
- 메모리 누수 여부를 공장/베이 반복 이동 시 검증한다.

## 11. 분석 이벤트

개인정보나 장비 원본 payload를 분석 도구로 전송하지 않는다. 허용되는 최소 이벤트는 다음과 같다.

- 공장뷰 진입/이탈
- 베이 선택/선택 해제
- 상태/공정 필터 사용
- 카메라 기본 시점 복원
- WebGL 대체 화면 진입

실제 분석 도구 도입 여부와 이벤트 전송 위치는 별도 승인 후 결정한다.

## 12. 수용 기준

1. LiDAR `ONLINE`, `OFFLINE`, `ERROR`, `CALIBRATING` 네 상태가 색상 외 텍스트/아이콘으로 구분된다.
2. 오류 장비가 포함된 베이는 공장 전체 시점에서 확대하지 않아도 식별된다.
3. 모든 베이에 경계와 라벨이 있으며 선택 시 해당 베이로 카메라가 자연스럽게 맞춰진다.
4. 선택 대상, 동일 stage 대상, 무관 대상이 서로 다른 강조 강도로 표현된다.
5. 빈 공간 또는 `Esc`로 선택을 해제할 수 있다.
6. 휠/트랙패드 조작이 갑자기 튀지 않고, 줌 한계에서 페이지 스크롤이 막히지 않는다.
7. LiDAR 상세에 heartbeat와 제공된 진단값이 표시되며 누락값을 추정하지 않는다.
8. `block_progress_rate`가 없는 경우 가짜 진행률을 표시하지 않는다.
9. 100%와 125% 글자 배율에서 주요 라벨과 상세 카드가 잘리거나 겹치지 않는다.
10. 키보드만으로 베이 선택, 상세 확인, 선택 해제가 가능하다.
11. WebGL 실패 시에도 베이 상태와 상세 정보에 접근할 수 있다.
12. `npm run lint`, `npm run boundaries`, `npm run build`가 통과한다.

## 16. 의존성과 준수사항

- 변경은 `processes/assembly` 내부를 우선하며 다른 공정 모듈을 직접 참조하지 않는다.
- 공통 3D/상태 컴포넌트 변경이 필요하면 `shared`가 특정 공정을 알지 않도록 일반 계약으로 설계하고 사전 협의한다.
- `module.ts`에는 무거운 3D 의존성을 정적 import하지 않는다.
- MQTT 어댑터를 프론트 또는 조립 판별 모듈에 새로 두지 않는다.
- Kepware/OPC-UA 경로를 도입하지 않는다.
- 구현 변경에는 대응 단위/컴포넌트 테스트를 포함한다.
