## 1. 개요

본 문서는 ISL v4의 **MQTT Agent와 Modbus Agent가 수집해야 할 태그**를 메시지 유형별로 열거하고, 각 유형의 tag id / value 목업을 정의한다.

- **목적:** ISL의 수집 모델은 선등록이다 — 태그를 Engine에 먼저 등록해야 Agent가 구독·폴링을 시작한다. 「필드 인터페이스 정의서」는 태그 ID의 **패턴**과 **수량 산식**까지만 정했으므로, 벤더와 등록 방식을 협의하고 필드 서비스·ISL DB Provider·판별 서비스가 같은 태그 ID를 바라보게 하려면 실제 **전개 목록**과 **값 예시**가 필요하다. 본 문서가 그 역할을 맡는다.
- **범위:** 조립·선행의장의 MQTT 메시지 3계열(장비 상태·인식 결과·파이프라인 산출물)과 선행도장의 Modbus 운전 태그 6종. 가공권역, 레거시 테이블 규격, Hot Data DB 적재 스키마, 판별 규칙은 대상이 아니다.
- **대상 독자:** ISL 벤더(MQTT Agent 구독·Modbus Agent 폴링 설정 담당), 필드 서비스 개발자(리옵스), ISL DB Provider 개발자, 권역별 판별 서비스 개발자.
- **근거 자료:** 「필드 인터페이스 정의서」 §4(식별 계층·토픽 설계)·§5(선등록 모델·태그 인벤토리)·§6(조립·선행의장 메시지 명세)·§7(선행도장 태그 명세)·§8(장비 마스터) / 「시스템 인터페이스 정의서」 `ASM-IF01`·`OUT-IF01`·`PNT-IF01` / `AGENTS.md`.

## 2. 문서 체계와 참조 관계

> **본 문서는 「필드 인터페이스 정의서」의 하위 문서다.** 태그 명명 규칙, 토픽 설계, 페이로드 스키마, 장비 마스터 필드는 그 문서가 유일한 소스이고, 본 문서는 그 규칙을 **전개**하고 **예시**를 붙일 뿐이다. 규칙이 바뀌면 본 문서의 전개표·목업을 함께 갱신한다.

| 문서 | 정의하는 것 | 본 문서와의 관계 |
|---|---|---|
| 시스템 인터페이스 정의서 | IF-ID 채번, 송·수신 시스템, 프로토콜, 주기, 인증 | 본 문서는 `ASM-IF01`·`OUT-IF01`·`PNT-IF01`을 **참조만** 하며 IF-ID를 채번하지 않는다 |
| 필드 인터페이스 정의서 | 토픽·태그 명명 규칙, 페이로드 스키마, 선등록 모델, 장비 마스터 | 본 문서의 상위. 규칙은 그쪽, 전개·예시는 이쪽 |
| **본 문서(필드 태그 목록)** | 선등록 태그 ID 전개표, 등록 수량, 장비 마스터 샘플, tag id / value 목업 | — |
| 권역별 기능 정의서 | 기능ID 단위 판별 규칙 | 본 문서의 태그가 판별 입력이 되지만 판별 규칙은 다루지 않는다 |

운영 규칙은 다음과 같다.

1. 본 문서에서 **IF-ID를 채번하지 않는다.** 세 MQTT 계열이 하나의 물리 채널(`ASM-IF01`/`OUT-IF01`)을 공유하는 근거는 「필드 인터페이스 정의서」 §2를 따른다.
2. 태그 ID 세그먼트는 소문자, payload enum 값은 대문자를 관례로 한다(「필드 인터페이스 정의서」 §5.1).
3. 모델명·벤더명·시리얼은 태그 ID·payload에 넣지 않고 장비 마스터(§5.2)에만 둔다(벤더 비종속 원칙).
4. 목업(§5.3)의 tag_id는 §4 전개표의 태그 ID와 1:1로 대응해야 하며, 어느 한쪽만 고치지 않는다.

## 3. 수집 주체별 태그 분류

ISL에 저장되는 최종 형태는 두 유형 모두 **태그ID / value**이지만, 태그 ID가 만들어지는 자리와 value의 모양이 다르다.

### 3.1 ISL MQTT Agent 구독 태그 — 메시지형(조립·선행의장)

- 태그 ID = **MQTT 토픽** 그대로. Agent는 등록된 태그 ID를 토픽으로 구독한다.
- value = **JSON payload 통째**(중첩 객체 포함)가 1개 태그 값으로 들어간다.
- 브로커는 EMQX 2식(조립용·의장용)으로 분리되므로, 태그 목록에 어느 브로커의 토픽인지를 함께 적는다(`broker` 속성).
- 시각 정보(occurred_at·ingested_at)와 레코드 유니크 키(idempotency_key)는 payload 안에 있다.

### 3.2 ISL Modbus Agent 폴링 태그 — 태그형(선행도장)

- 태그 ID = `{site}/painting/{dock}/{bay}/{device_role}/{device_id}/{metric}` 슬래시 계층 태그명 전체.
- value = **스칼라**(bool / float / int / enum 문자열). 단위는 태그 정의의 고정 속성이며 값과 함께 흐르지 않는다.
- 시각 정보는 태그 값에 붙는 **폴링 타임스탬프**가 맡고, idempotency 개념은 없다.
- register 주소 ↔ metric 매핑은 Modbus Agent의 register map 설정에 두고 태그 ID에는 넣지 않는다. ⚠️ register map 미확보.

### 3.3 태그 레코드 공통 속성

전개표(§4)의 각 태그가 갖는 속성이다. ISL 벌크 등록 입력을 만들 때 이 속성 집합을 레코드 스키마로 쓴다.

| 속성 | 값 | 설명 |
|---|---|---|
| tag_id | 문자열 | ISL 태그 ID. 메시지형은 MQTT 토픽, 태그형은 계층 태그명 |
| channel | DEVICE_STATUS / OBSERVATION / PIPELINE_ARTIFACT / PAINTING_OPERATION | 메시지 유형(본 문서의 분류 축) |
| collection_type | MESSAGE / TAG | 수집 유형(§3.1 / §3.2) |
| agent | MQTT_AGENT / MODBUS_AGENT | 수집 주체 |
| broker | emqx-assembly / emqx-outfitting / null | 메시지형이 publish되는 EMQX 인스턴스. 태그형은 null |
| zone | assembly / outfitting / painting | 권역 |
| related_if_id | ASM-IF01 / OUT-IF01 / PNT-IF01 | 「시스템 인터페이스 정의서」 채널 참조 |
| value_type | JSON / bool / float / int / enum | 값 자료형 |
| unit | %RH / °C / min / null | 태그형만. device_role로 확정되는 고정 속성 |
| derived_from | device_registry / shop_bay | 태그 ID의 등록 원천(§4.5) |
| device_role · device_id · shop · bay · metric | 해당 시 | 태그 ID 세그먼트의 분해값 |

## 4. 메시지 유형별 태그 리스트

아래 전개표는 **예시 구역 가정**(§5.1) 아래에서 만든 것이다. shop/bay 목록이 확정되면 같은 규칙으로 구역 수만큼 늘어난다(§4.5).

### 4.1 장비 상태 — `ot/device/{zone}/{device_role}/{device_id}/status`

**세그먼트 enum**

| 세그먼트 | 허용 값 | 비고 |
|---|---|---|
| zone | assembly / outfitting | 도장 PLC는 MQTT를 경유하지 않으므로 이 채널에 없다 — 통신 상태는 §4.4의 modbus_link·fault_code로 수집 |
| device_role | lidar / pan_tilt / edge_pc / inference_ws / vision_ocr | payload의 device_role은 대문자(`LIDAR` 등) |
| device_id | 장비 마스터(§5.2)에 등록된 값 | 태그 ID의 유일한 registry 종속 세그먼트 |

**예시 전개표** (장비 마스터 샘플 9대에서 파생)

| # | tag_id | broker | value |
|---|---|---|---|
| 1 | `ot/device/assembly/lidar/LDR-GJ-A1B3-01/status` | emqx-assembly | 장비 상태 JSON (`LIDAR` raw_payload) |
| 2 | `ot/device/assembly/pan_tilt/PTZ-GJ-A1B3-01/status` | emqx-assembly | 장비 상태 JSON (`PAN_TILT` raw_payload) |
| 3 | `ot/device/assembly/edge_pc/EDG-GJ-A1B3-01/status` | emqx-assembly | 장비 상태 JSON (`EDGE_PC` raw_payload) |
| 4 | `ot/device/assembly/inference_ws/INF-GJ-A1-01/status` | emqx-assembly | 장비 상태 JSON (`INFERENCE_WS` raw_payload) |
| 5 | `ot/device/assembly/vision_ocr/OCR-GJ-A1-01/status` | emqx-assembly | 장비 상태 JSON (`VISION_OCR` raw_payload) |
| 6 | `ot/device/outfitting/lidar/LDR-GJ-O1B2-01/status` | emqx-outfitting | 장비 상태 JSON (`LIDAR` raw_payload) |
| 7 | `ot/device/outfitting/pan_tilt/PTZ-GJ-O1B2-01/status` | emqx-outfitting | 장비 상태 JSON (`PAN_TILT` raw_payload) |
| 8 | `ot/device/outfitting/edge_pc/EDG-GJ-O1B2-01/status` | emqx-outfitting | 장비 상태 JSON (`EDGE_PC` raw_payload) |
| 9 | `ot/device/outfitting/inference_ws/INF-GJ-O1-01/status` | emqx-outfitting | 장비 상태 JSON (`INFERENCE_WS` raw_payload) |

- 선행의장에 `vision_ocr`은 없다 — Vision OCR은 조립공장 입구에만 설치된다. ⚠️ 선행의장에 GPU 워크스테이션(`inference_ws`)이 별도로 있는지는 확인이 필요하다. 「필드 인터페이스 정의서」 §6.3 인식 결과 메시지의 `device_ids.inference_ws`가 필수 문자열이므로 목록에는 포함했다.
- 등록 수는 장비 대수와 같다. 태그 ID는 장비 마스터 행에서 기계적으로 파생되므로 사람이 채번하지 않는다.

### 4.2 인식 결과 — `ot/sensor/{zone}/{shop}/{bay}/observation`

**세그먼트 enum**

| 세그먼트 | 허용 값 | 비고 |
|---|---|---|
| zone | assembly / outfitting | |
| shop / bay | ⚠️ 현장 레이아웃 확정 후 열거 | 예시: assembly1/bay3, outfitting1/bay2 |

**예시 전개표** (구역 1개씩 가정 — 조립 1 + 선행의장 1)

| # | tag_id | broker | value |
|---|---|---|---|
| 10 | `ot/sensor/assembly/assembly1/bay3/observation` | emqx-assembly | 인식 결과 JSON |
| 11 | `ot/sensor/outfitting/outfitting1/bay2/observation` | emqx-outfitting | 인식 결과 JSON |

- **토픽에 공정 단계(stage)가 없다.** 배열·가공·검사·출고(조립), 전장·관철(선행의장) 구분은 필드 publish 주체가 판별할 수 없는 값이고, 상태 전이·레거시 맥락을 가진 판별 서비스의 출력이다. 따라서 태그 ID와 payload 어디에도 두지 않으며, 구역당 태그는 1개다(「필드 인터페이스 정의서」 §4.3·§6.3). payload도 관측만 담는다 — 위치, scan_id·scanned_at, 매칭 CAD·신뢰도·인식 개수, 장비 체인, envelope.
- 태그 ID는 **채널 주소**이고 레코드 키가 아니다. 레코드 유니크함은 payload의 idempotency_key, 산출물과의 연결은 scan_id가 맡는다. hull_no·block_id·scan_id는 태그 ID에 절대 넣지 않는다(선등록 불가).
- 태그 하나에 연속 이벤트가 LastValue를 덮어써도 갱신 통지는 건마다 Provider로 나가므로 유실되지 않는다. ⚠️ 단, Engine의 Provider 호출 조건(write마다 / change 시만)은 벤더 확인이 필요하다.

### 4.3 파이프라인 산출물 — `ot/pipeline/{zone}/{shop}/{bay}/artifact`

| # | tag_id | broker | value |
|---|---|---|---|
| 12 | `ot/pipeline/assembly/assembly1/bay3/artifact` | emqx-assembly | 산출물 메타데이터 JSON |
| 13 | `ot/pipeline/outfitting/outfitting1/bay2/artifact` | emqx-outfitting | 산출물 메타데이터 JSON |

- 세 종류의 산출물(REGISTERED_PCD / TRANSFORMATION_MATRIX / SEGMENTED_PCD)이 **같은 태그**로 흐르고 payload의 artifact_type으로 구분한다. 종류별 태그 분리는 하지 않는다 — 구역별 스트림 하나로 충분하고 태그 수가 3배로 늘어날 이유가 없다.
- PCD 파일 본체는 싣지 않고 storage_uri 참조만 싣는다. ⚠️ 스토리지 위치·용량 정책 미정이므로 목업의 URI 스킴은 자리표시자다.

- 폴링 주기는 ⚠️ 미정이다. 목업에서는 모든 metric이 같은 폴링 시각을 갖는 것으로 두었다.

### 4.5 등록 수량 산정

| 채널 | 등록 원천(derived_from) | 산식 | 예시 가정 대입 | 실제 규모 추정 |
|---|---|---|---|---|
| 장비 상태 | device_registry | 조립·의장 장비 대수 | 9 | LiDAR ~350대 + pan_tilt(동수) + edge_pc·inference_ws·vision_ocr — ⚠️ 수백 대 규모 |
| 인식 결과 | shop_bay | zone별 shop×bay × 1 (공정 단계는 태그에 없음) | 2 | ⚠️ shop/bay 목록 확정 필요 |
| 파이프라인 산출물 | shop_bay | zone별 shop×bay × 1 | 2 | ⚠️ shop/bay 목록 확정 필요 |
| 도장 운전 | device_registry | PLC 대수 × 6 | 12 | 제습기·히터 대수 × 6 — ⚠️ 도크별 register map 편차 시 metric 수가 달라질 수 있음 |
| **합계** | | | **25** | |

> ⚠️ **LiDAR 대수 출처 불일치:** 「필드 인터페이스 정의서」는 조립 ~210 + 선행의장 ~140, 「OT Server 인프라 구성 및 CI/CD 설계서」 §2.4는 조립 340, `web-dashboard`의 설비 fixture는 LiDAR 337대·틸팅 모듈 337대를 담고 있다. 어느 쪽이 최신인지 확인해 일치시켜야 하며, 본 문서는 수량을 확정하지 않는다.

장비별 태그(장비 상태·도장 운전)는 사람이 채번하지 않고 **장비 마스터 행 → 태그 ID 파생 → Engine 등록** 순서로 프로비저닝한다. 구역별 태그(인식 결과·산출물)는 shop/bay 목록 확정 시 한 번 전개해 등록하고, 구역이 늘 때만 추가한다.

## 6. 제약사항 및 미확정 항목

「필드 인터페이스 정의서」 §9의 항목 중 본 문서에 직접 영향을 주는 것과, 본 문서에서 새로 생긴 가정을 모은다. 해소되면 해당 절을 갱신하고 변경 이력에 남긴다.

### 6.1 본 문서의 가정(상위 문서 확정 시 해소)

- ⚠️ **shop/bay 목록 미확정** — §4.2·§4.3 전개표는 예시 구역 1개씩이다. 목록 확정 시 구역 수만큼 전개하고 등록 수량(§4.5)을 실값으로 바꾼다.
- ⚠️ **device_id 채번 형식 추정** — §5.2의 형식은 정의서 예시 1건에서 유추한 것이다. 장비 마스터 설계에서 확정한다.
- ⚠️ **shop 단위 장비의 bay 표기 미규정** — inference_ws(공장 단위)·vision_ocr(입구)의 payload `bay` 값. 목업은 각각 `bay3`(임의 소속)·`entrance`(임의값)로 두었다.
- ⚠️ **선행의장의 inference_ws 존재 여부 미확인** — 인식 결과 메시지의 `device_ids.inference_ws`가 필수여서 목록에 포함했다. 없다면 정의서 §6.3 스키마를 `string | null`로 바꾸어야 한다.
- ⚠️ **스토리지 URI 스킴 자리표시자** — PCD 스토리지 위치·용량 정책 미정.
- ⚠️ **LiDAR 대수 출처 불일치** — §4.5 참조. 본 문서는 수량을 확정하지 않는다.
- ⚠️ **web-dashboard fixture와의 명명 차이** — §5.1 참조. 확정 시 한 방향으로 정렬한다.

### 6.2 ISL 벤더 확인 필요(본 문서의 전제)

- ⚠️ **태그화 방식** — "JSON payload 통째 = 1개 태그 값"을 전제한다. 필드별 분해 방식이라면 §4.1~§4.3의 value 정의와 목업 구조를 재검토한다.
- ⚠️ **벌크 등록 포맷·수 한계** — §4 전개표와 §3.3 속성 집합은 우리 측 초안이다. 등록 수단(API·CSV)과 한계 확인 후 등록 입력 형식을 정한다.
- ⚠️ **구독 단위** — Agent의 구독이 등록 태그 ID와 정확히 1:1인지(와일드카드 구독 지원 여부).
- ⚠️ **Provider 호출 조건** — write마다인지 change 시만인지. 도장 태그처럼 값이 장시간 같은 경우 시계열 적재에 영향이 있다.
- ⚠️ **태그 목록 변경 반영** — 장비 추가·교체 시 Agent 핫 리로드 여부.

### 6.3 장비·현장 확인 필요

- ⚠️ **도장 PLC register map 미확보** — metric 6종이 도크별로 다를 수 있다. 확보되면 §4.4 metric 표와 전개표를 도크별로 나눈다.
- ⚠️ **runtime_minutes_today 제공 주체** — PLC 제공인지 우리 계산인지.
- ⚠️ **도장 도크의 bay 개념** — 예시 `bay2`는 가정이다.
- ⚠️ **Modbus 폴링 주기 미정** — 목업은 단일 폴링 시각만 보인다.
- ⚠️ **인식 결과 raw_payload 항목 확정 필요** — `reference_cad_id`·`match_confidence`·`detected_count`가 추론 서비스의 실제 출력과 일치하는지, `block_progress_rate`를 유지할지(「조립 기능 정의서」는 형상 인식 + 카운팅 관점) 리옵스 확인이 필요하다. 확인 결과에 따라 §5.3 예시를 갱신한다.
