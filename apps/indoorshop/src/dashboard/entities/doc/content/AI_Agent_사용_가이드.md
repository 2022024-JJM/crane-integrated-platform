## 1. 목적 및 적용 범위

본 프로젝트는 **대부분의 코드를 AI 코드 Agent(Claude Code, Codex, Antigravity 등)에게 위임**해서 작성할 예정이다. 팀원·외주 인력이 서로 다른 Agent를 혼용하더라도 결과물의 품질과 아키텍처 일관성이 유지되도록, 공통 규칙과 검증 절차를 본 문서에 정의한다.

대상: 프로젝트에 참여하는 전체 개발 인력(박준상 PL, 박순영 PL, 조범희 PL, 김태상 프로, 외주 인력 포함).

## 2. 공통 컨텍스트 관리 — AGENTS.md / CLAUDE.md

AI Agent마다 프로젝트 컨텍스트를 읽는 파일명이 다르다.

| Agent | 읽는 파일 |
|---|---|
| Claude Code | `CLAUDE.md` |
| Codex | `AGENTS.md` |
| Antigravity | `AGENTS.md` |

여러 도구를 혼용하면서 규칙을 한 곳에서만 관리하기 위해, 본 레포는 다음 구조를 따른다.

- **`AGENTS.md`**: 모든 프로젝트 규칙(기술 스택, 모듈 의존성, 커밋 컨벤션, 보안, 테스트 정책 등)을 담는 **캐노니컬 소스**. Codex, Antigravity는 이 파일을 직접 읽는다.
- **`CLAUDE.md`**: `@AGENTS.md` import 한 줄 + Claude Code 전용 설정(Skill, Hook 등)만 담는 얇은 래퍼. Claude Code는 이 파일을 읽으면서 import된 `AGENTS.md` 내용을 그대로 적용받는다.

**원칙: 규칙은 `AGENTS.md`에만 작성한다.** `CLAUDE.md`에 같은 내용을 복제하지 않는다 — 두 곳에 따로 쓰면 한쪽만 갱신되는 drift가 반드시 생긴다.

> **참고:** AGENTS.md는 OpenAI Codex, Google(Antigravity/Jules), Cursor, Amp, Factory 등이 함께 만든 오픈 표준으로, Linux Foundation 산하 Agentic AI Foundation이 관리한다. Claude Code는 이 파일을 자동으로 읽지 않으므로 `@AGENTS.md` import 패턴이 필요하다 (Anthropic 공식 권장 방식).

## 3. 코드 리뷰 및 검증 책임

- **"Agent가 작성했으니 검증을 생략한다"는 절대 허용하지 않는다.** PR을 올린 사람이 그 코드의 검증 책임을 진다.
- 리뷰어는 다음을 특히 확인한다 (Agent가 자주 놓치는 부분):
  - `ot-pipeline-*` 모듈 간 직접 의존 여부 (AGENTS.md 모듈 의존성 규칙 위반)
  - 가공/도장 zone에 불필요한 MQTT 구독 로직이 들어갔는지 (zone별 특이사항 위반)
  - 하드코딩된 자격증명/내부 정보 포함 여부
  - State Machine 규칙이 코드에 하드코딩되지 않고 외부 yml로 분리됐는지
- PR 설명에 **어떤 Agent로 작업했는지(Claude Code/Codex/Antigravity/직접 작성)** 를 표기한다 — 문제 발생 시 원인 추적과 도구별 품질 비교에 활용.
- 동일 PR 내에서 Agent가 생성한 코드와 사람이 직접 수정한 부분이 섞여 있다면, 리뷰 코멘트에서 구분해 표시하는 것을 권장한다.

## 4. 테스트 정책

코드의 상당 부분을 Agent가 작성하므로, **테스트가 사람의 코드 이해를 대신하는 1차 안전망**이 된다.

- 모든 PR은 변경 사항에 대한 단위 테스트를 포함한다. 테스트 없는 PR은 기본적으로 머지하지 않는다.
- 외부 연동(JDBC, MQTT, RFC) 코드는 mock/fake 기반 테스트를 우선하고, 실제 연동 테스트는 별도 통합 테스트 단계로 분리한다.
- 모듈 의존성 규칙처럼 반복적으로 어겨지기 쉬운 규칙은, 가능하면 빌드 단계에서 자동 검출되도록 한다 (예: ArchUnit으로 `ot-pipeline-*` 간 의존 금지를 테스트 코드화). 도입 여부와 우선순위는 팀 내 별도 논의로 결정한다.

## 5. 민감정보 처리

- DB 자격증명, SAP RFC 연동 정보, 한화오션 비공개 문서(제안서, 협의목록 등)를 Agent 프롬프트나 컨텍스트에 그대로 붙여넣지 않는다.
- `.env.*.example`만 커밋하고 실값은 `.gitignore` 처리한다.
- 외주 인력에게는 이 기준을 동일하게 적용하며, 필요 시 더 엄격한 접근 제어(예: 운영 DB 자격증명 미공유)를 추가로 적용할지는 PM이 별도 결정한다.
- 클라우드 기반 Agent(Codex, Antigravity 등)에 코드/데이터가 전송되는 것이 사내 보안 정책상 문제가 없는지 사전 확인이 필요하다 (특히 한화오션 발주 프로젝트라는 점에서, 외부 전송 가능 여부를 보안팀/계약 조건과 한 번 확인 권장).

## 6. 도구별 작업 배분 가이드

세 도구는 강점이 다르므로, 작업 유형에 맞춰 선택하는 것을 권장한다 (강제 규칙은 아니며, 팀 경험이 쌓이면 갱신).

| 작업 유형 | 권장 도구 | 이유 |
|---|---|---|
| 아키텍처 판단이 필요한 멀티파일 리팩토링, 모듈 경계 작업 | Claude Code | 코드베이스 전반의 맥락을 깊게 추론하는 데 강점 |
| 스펙이 명확한 기능 구현 (예: 정해진 인터페이스에 맞춘 CRUD, 정형화된 변환 로직) | Codex | 명확한 스펙 기반 작업에서 실행 속도와 비용 효율이 좋음 |
| Google 생태계 연동 작업이 생기는 경우 | Antigravity | 아직 팀 내 실사용 경험이 적어 — 단순/저위험 작업부터 시작해 검증 권장 |

> **참고:** Claude Code는 토큰 소모가 Codex 대비 큰 편으로 보고되고 있어, 단순/반복 작업까지 전부 Claude Code에 맡기면 비용이 빠르게 늘 수 있다. 7장의 비용 관리와 함께 고려한다.

## 7. 비용 / 토큰 관리

- 각 Agent 도구의 월별 사용량(크레딧/비용)을 PM이 주기적으로 확인한다.
- 사용량이 예산을 초과할 조짐이 보이면, 단순 작업은 비용 효율이 높은 도구로 유도하는 등 6장의 작업 배분 가이드를 조정한다.
- 팀원별 사용량이 크게 차이 나는 경우, 사용 패턴(어떤 작업에 어떤 도구를 썼는지)을 공유해 베스트 프랙티스를 맞춘다.

## 8. 변경 관리

- `AGENTS.md`, `CLAUDE.md`, 본 가이드 문서는 모두 일반 코드와 동일하게 **PR 리뷰를 거쳐서만 변경**한다.
- `AGENTS.md` 변경 PR은 제목에 `[AGENTS.md]`를 prefix로 붙이고, 변경 내용을 팀 채널에 공지한다 (모든 Agent의 행동에 영향을 주는 변경이므로).
- 아키텍처 결정이 바뀌면(예: zone-서버 페어링, MQTT Broker 기술 스택 등) `AGENTS.md`를 가장 먼저 갱신한다 — Agent가 옛 정보를 기반으로 코드를 계속 생성하는 것을 막기 위함이다.
