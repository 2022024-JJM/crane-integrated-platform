## 1. 개요

본 문서는 내업 공정실적 자동수집 시스템(`ocean-process-system`) 개발에 참여하는 팀원이 로컬 개발환경을 구축하고, 모노레포 구조 안에서 모듈을 빌드·실행하며, 변경 사항을 배포 환경에 반영하는 절차를 안내한다.

대상 독자는 개발/구현을 담당하는 PL/Dev 인력(박준상, 박순영, 조범희, 정종민, 김태상 등)이며, 물리 인프라 구성과 그 설계 근거는 별도 문서인 「OT Server 인프라 구성 및 CI/CD 설계서」에서 다룬다.

### 1.1 적용 범위

- 레포지토리 구조 및 모듈 구성 (ocean-process-system 모노레포)
- 로컬 개발환경 셋업 및 모듈별 빌드/실행 방법
- 모듈 간 의존성 규칙
- State Machine 설정 관리 및 변경 반영 절차
- Git Flow 브랜치/태그/커밋 규칙
- 배포 절차 및 트러블슈팅

## 2. 기술 스택

### 2.1 언어/런타임 · 빌드

| 구분 | 선택 |
|---|---|
| 언어 | Java |

| 빌드 도구 | Gradle (멀티모듈, Git Flow 기반 브랜치 전략) |
| 애플리케이션 프레임워크 | Spring Boot |

### 2.2 메시징 / OT 미들웨어

| 구분 | 선택 |
|---|---|
| 메시지 브로커 | MQTT Broker(EMQX) — 조립용/의장용 2개 인스턴스 분리 (단일 아님, OT-Server-A/B에 각각 위치) |

### 2.5 인프라 (OS)

| 구분 | 선택 |
|---|---|
| OT Server OS | Ubuntu 24.04 LTS |

### 2.6 모니터링

| 구분 | 선택 |
|---|---|
| 메트릭/대시보드 | Prometheus + Grafana |

### 2.7 형상관리 / 협업

| 구분 | 선택 |
|---|---|
| 형상관리 | Git (모노레포, Git Flow) |

## 3. 레포지토리 구조

### 3.1 모노레포 전환 배경

기존에는 `ocean-ot-engine`, `ocean-rfid-preprocessor`, `ocean-rfid-tag-publisher` 등을 개별 레포로 관리하는 meta-repo 패턴을 검토하였으나, 전체 구성 모듈을 단일 레포에서 관리하는 모노레포 구조로 전환하였다. zone별 배포 단위는 유지하되, 소스 관리와 변경 이력 추적을 한 곳에서 일관되게 가져가기 위한 결정이다.

### 3.2 디렉토리 구조

```
ocean-process-system/
├── src/                              # 전체 소스 코드 루트 (언어 무관)
│   ├── settings.gradle               # Gradle 멀티모듈 — 아래 include 목록만 빌드 대상
│   ├── build.gradle
│   ├── gradle.properties
│   ├── ot-core/                      # 공유 State Machine 엔진 (라이브러리)
│   ├── ot-pipeline-fabrication/      # 가공
│   ├── ot-pipeline-assembly/         # 조립
│   ├── ot-pipeline-outfitting/       # 선행의장
│   ├── ot-pipeline-painting/         # 선행도장
│   ├── rfid-preprocessor/            # RFID 전처리 PC 로직
│   ├── rfid-tag-publisher/           # RFID MQTT publish — ⚠️ 기술 스택 미확정(Java가 아닐 수 있음), settings.gradle include 목록에는 없음
│   └── state-machine-configs/        # zone별 SM 설정 (source of truth)
│       ├── fabrication.yml
│       ├── assembly.yml
│       ├── outfitting.yml
│       └── painting.yml
├── deploy/                       # 배포 스크립트 및 compose 파일
└── docs/                         # 기존 ocean-inshop-process 문서 이관
```

> **참고:** `rfid-tag-publisher`는 `src/` 안에 같이 두지만 Gradle 멀티모듈 트리에는 포함하지 않는다 (`settings.gradle`의 `include` 목록에 없음 — Gradle은 거기 없는 디렉토리는 그냥 무시한다). 기술 스택이 확정되면 해당 언어의 빌드 설정(예: `package.json`, `requirements.txt` 등)을 `rfid-tag-publisher/` 안에 독립적으로 둔다.

### 3.3 모듈 구성 및 산출물

| 모듈 | 역할 | 산출물 |
|---|---|---|
| ot-core | 공유 State Machine 엔진, 도메인 모델, OT DB I/F | jar (라이브러리, bootJar 비활성화) |
| ot-pipeline-fabrication | 가공 공정 인식/판별 (Legacy DB 연동 중심) | bootJar → 독립 프로세스 |
| ot-pipeline-assembly | 조립 공정 인식/판별 (LiDAR/Vision 연동) | bootJar → 독립 프로세스 |
| ot-pipeline-outfitting | 선행의장 공정 인식/판별 (RFID 연동) | bootJar → 독립 프로세스 |
| ot-pipeline-painting | 선행도장 공정 인식/판별 (PLC 연동) | bootJar → 독립 프로세스 |
| rfid-preprocessor | RFID 태그 debounce/중복제거 전처리 | bootJar → 독립 프로세스 |

> **rfid-tag-publisher** (RFID 전처리 결과 MQTT publish)는 기술 스택이 미확정이라 위 Gradle 모듈 표에서 제외했다. Java로 확정되면 표와 `settings.gradle`에 추가한다.

> **참고:** 가공공정 항목은 WBS_2.0에서 Legacy DB 연동 도메인으로 별도 처리되어 있으나, 레포 구조상으로는 `ot-pipeline-fabrication` 모듈로 동일하게 관리한다.

### 3.4 모듈 내부 패키지 구조 (헥사고날 아키텍처)

Java 기반 모듈(`ot-core`, `ot-pipeline-*`, `rfid-preprocessor`)의 내부 패키지는 헥사고날 아키텍처를 따른다. 핵심 원칙: **`domain/`은 프레임워크(Spring 등)를 import하지 않는다.** Spring 의존은 `infrastructure/`, `adapter/`, `config/`에만 둔다.

#### 3.4.1 ot-core (도메인 라이브러리)

```
src/ot-core/src/main/java/com/hanwha/ocean/otcore/
├── domain/
│   ├── model/                  # Zone, ProcessEvent, ProcessState, Transition 등 순수 도메인 모델
│   ├── statemachine/           # StateMachineEngine — 상태 전이 평가 로직 (순수 Java, Spring 의존 없음)
│   └── exception/
├── application/
│   ├── port/
│   │   ├── in/
│   │   │   └── EvaluateProcessEventUseCase.java   # zone 모듈이 호출하는 유일한 진입점
│   │   └── out/
│   │       └── StateMachineConfigRepository.java  # SM yml 로딩 인터페이스
│   └── service/
│       └── DefaultEvaluateProcessEventService.java # UseCase 구현 (StateMachineEngine 사용)
└── infrastructure/
    └── config/
        ├── YamlStateMachineConfigRepository.java   # StateMachineConfigRepository 기본 구현 (모든 zone 공통 로직)
        └── StateMachineProperties.java             # @ConfigurationProperties(prefix="state-machine")
```

#### 3.4.2 ot-pipeline-{zone} 공통 템플릿 (4개 zone 모듈 동일 적용)

```
src/ot-pipeline-assembly/src/main/java/com/hanwha/ocean/pipeline/assembly/
├── domain/                         # zone 고유 보강 모델 (필요한 경우만 — 대부분 ot-core 도메인 재사용)
├── application/
│   ├── port/
│   │   ├── in/
│   │   │   └── JudgeAssemblyProcessUseCase.java     # Provider 진입점 — OT Core(ISL Engine)가 호출
│   │   └── out/
│   │       ├── HotDataRepository.java                # Hot DB 저장/조회
│   │       ├── LegacyDataGateway.java                 # Legacy DB 연동 (가공은 필수, 나머지는 선택)
│   │       └── ProcessResultNotifier.java             # 판별 결과 전달 — ⚠️ 프로토콜 미확정
│   └── service/
│       └── AssemblyProcessJudgeService.java           # UseCase 구현, ot-core의 EvaluateProcessEventUseCase 호출
├── adapter/
│   ├── in/
│   │   └── provider/
│   │       └── AssemblyProviderEndpoint.java          # ⚠️ REST/RPC 등 실제 프로토콜 미확정
│   └── out/
│       ├── persistence/
│       │   ├── HotDataJdbcRepository.java
│       │   └── entity/
│       ├── legacy/
│       │   └── LegacyDbJdbcGateway.java
│       └── notifier/                                  # TBD — ISL4 Provider SDK 연동 방식 확정 후 구현
└── config/
    ├── AssemblyApplication.java                        # @SpringBootApplication
    └── BeanWiringConfig.java                            # Port ↔ Adapter 연결
```

`ot-pipeline-fabrication`, `ot-pipeline-outfitting`, `ot-pipeline-painting`도 패키지명(`com.hanwha.ocean.pipeline.{zone}`)과 클래스 prefix만 바꿔 동일 구조를 적용한다.

> **참고:** 의도적으로 MQTT 어댑터를 두지 않는다. 다이어그램 기준 MQTT Broker 구독은 ISL4 Agent(벤더 컴포넌트)가 처리하고, zone 모듈은 OT Core가 호출하는 Provider로만 동작한다 — `ot-pipeline-painting`에 MQTT 코드가 들어가면 안 된다는 AGENTS.md 규칙과도 일치한다.
>
> ⚠️ 표시한 `ProcessResultNotifier`/`AssemblyProviderEndpoint`는 OT Server 인프라 설계서의 "OT-Server↔ISL Server 결과 전달 프로토콜" 미확정 항목과 연결된다. 포트(인터페이스)만 먼저 정의하고, 구현체는 프로토콜이 확정된 후 채운다.

src/rfid-preprocessor/src/main/java/com/hanwha/ocean/rfid/preprocessor/

## 4. 로컬 개발환경 셋업

### 4.1 사전 요구사항

- JDK 21
- Gradle (Wrapper 사용, 별도 설치 불필요)
- Docker / Docker Compose (로컬에서 OT DB, EMQX 등 의존 서비스 기동 시)

> **참고:** JDK 17 대신 JDK 21을 채택한 이유 — Oracle JDK 17 Premier Support는 2026년 9월 종료되어 본 프로젝트 오픈 시점과 맞물리는 반면, JDK 21은 2028년 9월까지 지원된다. 또한 JDK 21의 Virtual Threads는 JDBC/MQTT 클라이언트 등 I/O 바운드 워크로드가 많은 본 시스템 구조에 유리하다 (Spring Boot 3.2 이상에서 `spring.threads.virtual.enabled=true`로 활성화 가능).

### 4.2 settings.gradle

```groovy
rootProject.name = 'ocean-process-system'
include 'ot-core',
        'ot-pipeline-fabrication',
        'ot-pipeline-assembly',
        'ot-pipeline-outfitting',
        'ot-pipeline-painting',
        'rfid-preprocessor'
        // rfid-tag-publisher는 기술 스택 미확정이라 제외 (Java로 확정되면 추가)
```

### 4.3 루트 build.gradle (공통 설정)

```groovy
subprojects {
    apply plugin: 'org.springframework.boot'
    apply plugin: 'io.spring.dependency-management'
    apply plugin: 'java'

    sourceCompatibility = '21'

    repositories { mavenCentral() }

    dependencies {
        implementation 'org.springframework.boot:spring-boot-starter'
    }
}
```

### 4.4 모듈별 빌드/실행

`settings.gradle`과 Gradle Wrapper(`gradlew`)가 모두 `src/` 아래에 있으므로, 먼저 `src/` 디렉토리로 이동한 뒤 실행한다.

전체 모듈을 한 번에 빌드하려면:

```bash
cd src
./gradlew build
```

변경된 특정 모듈만 빌드하려면:

```bash
./gradlew :ot-pipeline-assembly:build
./gradlew :ot-pipeline-assembly:bootJar
```

로컬에서 특정 zone 모듈을 직접 실행하려면 (OT DB, EMQX 등 의존 서비스가 로컬에 떠 있어야 함):

```bash
./gradlew :ot-pipeline-assembly:bootRun
```

## 5. 모듈 의존성 규칙

### 5.1 의존 방향

모든 `ot-pipeline-*` 모듈은 `ot-core`에만 의존하며, `ot-pipeline-*` 모듈 간 직접 의존은 금지한다. 순환 의존을 막고, zone별 독립 배포 단위라는 설계 원칙을 코드 구조에도 그대로 반영하기 위함이다.

```
ot-pipeline-assembly     ──depends on──>  ot-core
ot-pipeline-fabrication  ──depends on──>  ot-core
ot-pipeline-outfitting   ──depends on──>  ot-core
ot-pipeline-painting     ──depends on──>  ot-core

(ot-pipeline-* 모듈 간 직접 참조 금지)
```

### 5.2 각 모듈의 build.gradle 의존성 선언

```groovy
// ot-pipeline-assembly/build.gradle
dependencies {
    implementation project(':ot-core')
}
```

### 5.3 ot-core 변경 시 영향 범위

`ot-core`는 모든 zone 모듈이 의존하는 공유 라이브러리이므로, `ot-core` 변경 시에는 4개 zone 모듈 전체를 재빌드해야 한다. CI 파이프라인에서 `ot-core` 변경분은 전체 재빌드 트리거로 설정한다 (자세한 내용은 「OT Server 인프라 구성 및 CI/CD 설계서」의 CI/CD 파이프라인 섹션 참조).

## 6. State Machine 설정 관리 방식

### 6.1 기본 원칙

State Machine 인식 규칙은 코드에 하드코딩하지 않고 YAML 기반 외부 설정으로 분리한다. Key User 확인(C-01) 이후에도 공정존별 규칙이 계속 조정될 가능성이 높으므로, 재빌드 없이 설정만 교체·반영할 수 있는 구조를 채택한다.

### 6.2 설정 파일 위치와 소스 오브 트루스

`state-machine-configs/` 디렉토리를 변경 이력의 source of truth로 두고, 운영 환경에는 별도 외부 경로(컨테이너 볼륨 마운트)로 배포한다.

```
state-machine-configs/
├── fabrication.yml
├── assembly.yml
├── outfitting.yml
└── painting.yml
```

### 6.3 애플리케이션에서의 참조 방식

```yaml
# application.yml
state-machine:
  config-path: ${STATE_MACHINE_CONFIG_PATH}/assembly.yml
```

```java
@ConfigurationProperties(prefix = "state-machine")
public class StateMachineProperties {
    private String configPath;
}
```

### 6.4 변경 반영 절차

1. Key User 협의 결과를 `state-machine-configs/{zone}.yml`에 반영하고 PR로 diff 리뷰
2. 머지 후 `sync-configs.sh` 스크립트로 대상 서버에 rsync
3. 해당 zone 컨테이너만 restart (재빌드/재배포 불필요)

> **참고:** 진행중인 공정 판별 로직이 룰 변경 중간에 끼면 일관성 문제가 생길 수 있어, 초기 단계에서는 핫리로드 없이 "재시작 반영" 방식을 사용한다. 운영 안정화 후 파일 watcher 기반 핫리로드 적용을 검토한다.

## 7. Git Flow 가이드

모노레포 + zone별 독립 배포 구조이므로, 일반적인 Git Flow에 모듈 단위 규칙을 추가로 적용한다.

### 7.1 브랜치 전략

| 브랜치 | 용도 |
|---|---|
| main | 운영 배포 기준 브랜치 |
| develop | 통합 개발 브랜치 |
| feature/{모듈}-{설명} | 기능 개발 (예: feature/ot-pipeline-assembly-lidar-event) |
| release/{모듈}-v{버전} | 모듈 단위 배포 준비 |
| hotfix/{모듈}-{설명} | 운영 중 긴급 수정 |

### 7.2 모듈별 vs 레포 전체 — 적용 범위

zone별 독립 배포 단위이므로, release 브랜치와 태그는 레포 전체가 아니라 변경된 모듈 단위로 생성하는 것을 원칙으로 한다. 레포 전체에 `release/v1.2.0`과 같이 버전을 붙이면, 변경되지 않은 다른 zone 모듈까지 배포 대상처럼 오인될 수 있다.

### 7.3 커밋 메시지 규칙

모듈 경로를 prefix로 표기한다.

```
[ot-pipeline-assembly] LiDAR 이벤트 판별 로직 추가
```

### 7.4 모듈별 release 태깅 규칙

```
ot-pipeline-assembly-v1.2.0
rfid-preprocessor-v0.3.0
ot-core-v1.0.0
```

> **참고:** 이 태깅 규칙은 CI/CD에서 어떤 모듈을 빌드/배포할지 판단하는 트리거 기준이 된다. 트리거 로직의 상세 내용은 「OT Server 인프라 구성 및 CI/CD 설계서」를 참조한다.

## 8. 배포 절차

### 8.1 물리 서버 개요

OT 영역은 물리적으로 4대 서버로 구성된다: Hot Data DB 서버, ISL Server(ISL Engine/Dashboard, RFC/Oracle Agent, Thingworx Provider, 도장 Modbus Agent), OT-Server-A(조립+도장, MQTT Broker[조립용]+조립 Agent 포함), OT-Server-B(가공+선행의장, MQTT Broker[의장용]+의장 Agent 포함). MQTT Broker는 단일이 아니라 조립용/의장용 2개 인스턴스로 분리되어 있다 (내부적으로 EMQX를 메시징 구현체로 사용). 서버 구성 및 배치 근거는 「OT Server 인프라 구성 및 CI/CD 설계서」에서 상세히 다룬다.

### 8.2 배포 스크립트 구조

```
deploy/
├── docker-compose.db.yml
├── docker-compose.isl.yml
├── docker-compose.server-a.yml
├── docker-compose.server-b.yml
├── .env.{db,isl,server-a,server-b}.example
└── scripts/
    ├── deploy-all.sh
    ├── sync-configs.sh
    └── healthcheck-all.sh
```

### 8.3 전체 배포 (deploy-all.sh)

```bash
#!/bin/bash
set -e
source ../hosts.conf

echo "[1/3] Hot Data DB 기동"
ssh $HOST_DB "cd $DEPLOY_PATH && docker compose -f docker-compose.db.yml up -d"

echo "[2/3] ISL 서버 기동 (ISL Engine/Dashboard, RFC/Oracle Agent, Thingworx Provider, 도장 Modbus Agent)"
ssh $HOST_ISL "cd $DEPLOY_PATH && docker compose -f docker-compose.isl.yml up -d"

echo "[3/3] OT-Server-A/B 기동 (MQTT Broker + Agent + 실적판별서비스, zone별 로컬 구성)"
ssh $HOST_SERVER_A "cd $DEPLOY_PATH && docker compose -f docker-compose.server-a.yml up -d"
ssh $HOST_SERVER_B "cd $DEPLOY_PATH && docker compose -f docker-compose.server-b.yml up -d"
```

### 8.4 설정 동기화 (sync-configs.sh)

```bash
#!/bin/bash
set -e
source ../hosts.conf

declare -A ZONE_MAP=(
  [assembly]=$HOST_SERVER_A
  [painting]=$HOST_SERVER_A
  [fabrication]=$HOST_SERVER_B
  [outfitting]=$HOST_SERVER_B
)

for zone in "${!ZONE_MAP[@]}"; do
  host=${ZONE_MAP[$zone]}
  rsync -avz ../../src/state-machine-configs/${zone}.yml ${host}:${CONFIG_PATH}/${zone}.yml
  ssh $host "docker compose restart ot-pipeline-${zone}"
done
```

> **참고:** ZONE_MAP은 8.1절의 zone-서버 페어링(조립+도장 / 가공+의장)을 그대로 반영한다. 페어링이 바뀌면 이 매핑만 수정하면 된다.

### 8.5 헬스체크 (healthcheck-all.sh)

```bash
#!/bin/bash
source ../hosts.conf

echo "=== Hot Data DB ===";  ssh $HOST_DB   "docker exec hotdata-db pg_isready"
echo "=== ISL Server ===";   ssh $HOST_ISL  "curl -sf http://localhost:8090/actuator/health && echo OK"   # ISL Engine 포트 확정 필요
echo "=== OT-Server-A (MQTT Broker 조립용) ==="; ssh $HOST_SERVER_A "curl -sf http://localhost:8222/healthz && echo OK"
echo "=== OT-Server-A (조립/도장 실적판별서비스) ==="; ssh $HOST_SERVER_A "curl -sf http://localhost:8080/actuator/health && curl -sf http://localhost:8081/actuator/health && echo OK"
echo "=== OT-Server-B (MQTT Broker 의장용) ==="; ssh $HOST_SERVER_B "curl -sf http://localhost:8222/healthz && echo OK"
echo "=== OT-Server-B (가공/의장 실적판별서비스) ==="; ssh $HOST_SERVER_B "curl -sf http://localhost:8080/actuator/health && curl -sf http://localhost:8081/actuator/health && echo OK"
```

> **참고:** 한 서버에 zone 2개씩 컨테이너가 뜨므로 actuator 포트가 충돌하지 않도록, 모듈별 포트를 `.env`에서 분리 관리한다 (예: 8080/8081). MQTT Broker가 OT-Server-A/B에 각각 위치하므로, 헬스체크도 서버별로 확인한다 (단일 ISL Server 헬스체크가 아님).

## 9. 트러블슈팅

### 9.1 healthcheck 실패 시 체크리스트

1. 해당 컨테이너 로그 확인 (`docker compose logs {서비스명}`)
2. DB/MQTT Broker 연결 정보(.env)가 올바른지 확인
3. OT DB·ISL 서버가 실제로 기동되어 있는지 healthcheck-all.sh로 별도 확인
4. 네트워크 경로(OT망 내 서버 간 통신) 차단 여부 확인

### 9.2 자주 발생하는 이슈

| 증상 | 주요 원인 및 확인 사항 |
|---|---|
| 컨테이너가 기동 후 바로 재시작 반복 | DB/MQTT Broker 연결 실패 시 `initialization-fail-timeout` 설정 누락 여부 확인 |
| State Machine 설정이 반영되지 않음 | sync-configs.sh 실행 후 해당 zone 컨테이너 restart 여부 확인 (파일만 교체하고 restart 누락 시 미반영) |
| 빌드 시 ot-core 변경이 zone 모듈에 반영 안 됨 | `cd src && ./gradlew clean` 후 재빌드, 또는 의존성 캐시 문제 확인 |
| actuator 헬스체크 포트 충돌 | 같은 서버 내 zone별 포트 분리 설정(.env) 확인 |
