# 골리앗 충돌방지 — 실물 센서(LiDAR·비전·PLC) 연동 계획

작성일: 2026-08-12

현재 충돌 감지 레이어는 시뮬레이션 소스로 구동된다. 이 문서는 실물 센서를
붙일 때 무엇이 필요한지, 무엇이 이미 준비돼 있는지를 정리한다.

관련 코드
- 스토어: `packages/features/src/3d/model/use-collision-guard-store.ts`
- 시뮬레이션(교체 대상): `packages/features/src/3d/model/use-collision-guard-simulation.ts`
- 렌더러: `packages/features/src/3d/ui/collision-guard.tsx`
- 존 설정: `apps/goliath-crane/src/pages/goliath-crane/config/goliath-collision-zone.ts`
- 기존 LiDAR 인프라: `apps/goliath-crane/src/pages/goliath-crane/{lib,model}/point-cloud*`

---

## 요약

`ingest()`의 push 기반 형태는 실물 연동에 적합하게 설계돼 있다. 다만 코드
주석이 오랫동안 "이 훅만 제거하고 브리지가 ingest()를 호출하면 된다"고
적어 온 것은 **작업량을 크게 과소평가한 표현**이었다(2026-08-12 수정됨).

시뮬레이션 훅은 데이터 소스만이 아니라 **좌표 프레이밍 · 존 진입/이탈
판정 · 트랙 수명 관리 · 타입 결정**의 네 책임을 함께 지고 있다. 훅을 지우면
네 가지가 같이 사라진다.

## 이미 준비된 것

retrofit이 어려웠을 부분들은 다행히 해결돼 있다.

| 항목 | 상태 |
|---|---|
| push 기반 ingest + 렌더러 보간 분리 | 관측 주기와 프레임 레이트가 이미 독립. 10~20Hz 실물 피드도 그대로 동작 |
| 크레인 이동 대응 | 존이 하드코딩이 아니라 크레인 실시간 포즈에서 파생됨 (`buildGoliathCollisionZones`) |
| 미터 단위 일급 취급 | 모든 거리를 m로 저작하고 `metersPerUnit`으로 환산. 축척 10배 차이 씬에서도 검증됨 |
| 리렌더 0회 아키텍처 | 트랙 수가 늘어도 저하 없음 |
| LiDAR 전송 인프라 | SOSLAB 2기 + fusion, protobuf 디코더, 재연결 백오프, 센서 레지스트리, `STALE_SENSOR_MS` |
| WebSocket 브리지 셸 | `use-realtime-websocket-bridge.ts`가 구독 + refcount 템플릿 |

## 선행 작업 (착수 순서 권장)

### 1. 좌표 변환 계층 — 블로커

현재 `ingest(id, type, x, z, ...)`의 x/z는 **이미 씬 world unit**이다.
시뮬레이션이 `zone.center`에서 출발하기 때문에 변환이 필요 없었다.

실물 LiDAR는 센서 로컬 프레임(m, Z-up, 원점=센서, 임의 yaw)으로 온다.
필요한 합성 체인:

1. 축 변환: ROS `(x, y, z_up)` → three.js `(x, z_up→y, y→z)` + 손잡이 방향 반전
2. 센서 외부 파라미터: 각 LiDAR의 다리 기준 yaw/pitch/roll + 레버암
3. 다리 로컬 → 월드: 크레인이 주행하므로 **매 프레임 갱신**
4. 미터 → unit: `METERS_PER_UNIT = 1.17`로 나눔
5. heading 프레임: 렌더러가 `rotation.y = -heading`으로 쓰므로 부호 반전 포함

주의: 현재 포인트클라우드 뷰어의 `SensorTransform`은 **수동 슬라이더 6개**로
눈대중 정렬하는 도구다(기본값 전부 0). 교정값을 영속화하는 저장소가 별도로
필요하다.

heading을 틀리면 객체가 뒤를 보고 렌더된다 — 그럴듯해 보이지만 조용히
틀린 상태이고, 진행 방향 화살표가 정확히 이 값을 표시한다.

### 2. 트랙 수명 관리 — 블로커

`DetectedTrack`에 **타임스탬프가 없다**. 그리고 `markLeaving()`을 호출하는
곳은 시뮬레이션 훅뿐이다.

실물 트래커는 "사라졌다" 이벤트 없이 그냥 보고를 멈추는 경우가 많다(가림,
추적 실패). 그러면 트랙은 `phase: 'active'`로 영원히 남고, 마지막 위치에
얼어붙는다. **위험 반경 안에서 멈추면 가짜 경보가 무한히 지속된다** —
안전 오버레이에서 가장 나쁜 실패 모드다(운영자가 경보를 무시하게 된다).

필요한 것:
- 트랙마다 `lastSeenAt` + 무보고 타임아웃 리퍼(약 0.5~1초 후 markLeaving)
- id 네임스페이스: `${sensorId}:${trackId}:${generation}`
  - 현재 `ingest()`는 같은 id를 무조건 같은 객체로 보고 `phase='active'`로
    **되살린다**. 트래커가 id를 재활용하면 이전 객체가 새 객체로 둔갑한다.
  - 시뮬레이션의 `sessionIdRef` 접두사는 리마운트 충돌만 막는다. 트래커의
    id 재사용은 못 막는다.
- split/merge 처리: merge로 흡수된 id는 markLeaving을 못 받아 유령이 된다

### 3. 존 진입/이탈 판정 이관 — 블로커와 함께

시뮬레이션의 `nearestZone` + `EXIT_HYSTERESIS_M`(5m) 판정은 시뮬레이션
로직이 아니라 **가드 로직**인데 시뮬레이션 파일에 있다. 브리지도 같은
판정을 써야 경계에서 깜빡이지 않으므로 공용 모듈로 분리한다.

### 4. 드레인 버퍼 — 중요

`ingest()`를 소켓 콜백에서 동기 호출하면 안 된다. 신규 id마다 `set()`이
호출되어 React 리렌더 + GLB 인스턴스 마운트가 소켓 스레드에서 발생한다.
센서 2대 × 20Hz × 30트랙이면 초당 1200회다.

같은 저장소에 이미 두 개의 참고 구현이 있다:
- `use-realtime-store.ts` — push 후 `useFrame`에서 `drainBuffer()`
- `point-cloud-stream-store.ts` — 버퍼 in-place mutate + 프레임 카운터 폴링

충돌 가드만 이 패턴이 빠져 있다. 함께 처리할 것:
- 같은 id의 중간 관측 coalescing
- `Map<string, DetectedTrack>` 인덱스 (현재 메시지마다 선형 스캔)
- 프레임당 add/remove를 `set()` 1회로 배치

### 5. 타입·신뢰도 — 중요

`DetectedObjectType`은 3개짜리 닫힌 enum이고 신뢰도가 없다.

- `'unknown'` 추가 필요 — 저신뢰 감지를 셋 중 하나로 오분류할 수 없다
- `confidence` 추가 — 렌더러의 `presence`(현재 순수 기하)에 자연스럽게
  연결된다. 신뢰도 낮으면 고스트로 표시
- **현재 `ingest()`는 기존 트랙의 `type`을 무시한다** — 중간 재분류가
  조용히 버려진다. 다만 순진하게 고치면 안 된다: type이 모델 GLB ·
  `OBJECT_HEIGHT` · 접지 앵커 크기 · 화살표 오프셋을 결정하므로 중간에
  바뀌면 메시가 팝한다. 히스테리시스를 걸어 지속적인 고신뢰 불일치일
  때만 전환할 것

### 6. 다중 센서 연관 — 중요

`ingest()`에 `sensorId` 파라미터가 없고 트랙에도 센서 필드가 없다.

존 두 개의 중심 간격은 123.9 unit인데 반경 합은 120이다 — 거의 맞닿아
있어서 **다리 사이를 지나는 사람은 양쪽 센서에 모두 잡힐 가능성이 높다**.
그러면 1m 떨어진 사람이 둘 렌더되고 HUD 개수도 부풀려진다.

필요: `sensorId` 추가 → 월드 프레임에서 게이팅 + 연관(NN 또는 헝가리안)
→ fused 트랙 계층. **1번(좌표 변환)이 선행되어야 의미가 있다** — 공통
프레임이 없으면 연관을 계산할 수 없다.

## 비전(카메라) 연동

`vision/types.ts`에 카메라 12채널(cam-1~12)이 이미 정의돼 있고 PiP·확대
뷰가 동작한다. 충돌 감지와의 연결 관점에서 결정할 것:

- **카메라를 감지 소스로 쓸 것인가, 확인 수단으로 쓸 것인가.** 후자라면
  트랙 클릭 시 해당 방위의 카메라를 띄우는 연결만 있으면 된다(구현 부담
  작음, 운영 가치 큼).
- 전자라면 LiDAR와 동일한 연관 문제가 카메라-LiDAR 간에도 생긴다.
  `cameraRadius`(32 unit) 필드가 이미 존재하나 현재 기본 숨김이다.

## PLC 연동

크레인 지표(하중·풍속·호이스트·트롤리)는 현재
`use-goliath-crane-data.ts`의 `applyLiveFluctuation`이 2초마다 난수
요동을 만든다. 실물 연동 시 이 함수를 제거하고 기존 실시간 WebSocket
경로(`cranesLiteWebSocketClient`, 키 포맷 `${craneId}:${tagCode}`)를 쓴다.
이쪽은 스칼라 태그값이라 **위 LiDAR 이슈들과 무관하게 난이도가 낮다**.

충돌 감지와의 접점: 크레인 주행 속도·방향을 PLC에서 받으면 TTC 계산의
입력이 된다(아래).

## 별건이지만 실물 연동 전에 권장

### 세버리티를 TTC 기반으로

현재 `trackSeverity()`는 순수 거리 판정이다.

```
dist <= zone.dangerRadius ? 'danger' : 'warning'
```

멀어지는 사람과 초속 7m로 접근하는 지게차가 같은 레벨로 뜬다.
시뮬레이션에서는 그럭저럭 보이지만, 실물 데이터가 들어오면 **오경보가
쏟아져 운영자가 경보를 무시하게 되는** 전형적 실패 경로다. heading과
speed는 이미 트랙에 있으므로 접근 성분만 계산하면 된다. PLC에서 크레인
자체 속도를 받으면 상대속도까지 반영 가능하다.

### 라벨 겹침 해소

해시 기반 높이 분산(5버킷)이 4트랙에서 81% 확률로 충돌하고, 분산 폭도
화면상 2.4px에 불과해 사실상 작동하지 않는다. 실물에서는 트랙 수가 더
늘어나므로 화면 공간 충돌 해소가 필요하다.

### 존 링 리마운트

`DetectionZoneRing`의 key가 존 중심 좌표다. **크레인 실시간 위치를
sceneInfo로 흘리는 순간 매 tick 링이 리마운트**되어 펄스·레이더 파장
상태가 리셋된다. key를 `zone.label`(L1/L2)로 바꾸고 center는 prop 갱신으로
따라가게 할 것.

## 작업량 감각

"훅 제거 + 브리지 연결"은 하루짜리다. 실제로는 변환/교정 계층, 수명 관리,
드레인 버퍼, 연관 계층이 각각 작은 모듈 하나씩이다. 1·2번은 안전 기능의
하드 선행 조건이다.
