# 3D 성능 품질 게이트 계획

작성일: 2026-09-01

3D 씬에 모델·로직을 추가했을 때 **성능이 얼마나 나빠졌는지를 변경마다 숫자로**
알 수 있게 하는 작업 지시서다. 이번 범위는 **브라우저·GPU 없이 오프라인으로 도는
1·2단계**까지이며, 실측 런타임(3단계)은 보안 검토가 필요해 분리했다.
**이 문서를 그대로 구현 에이전트에 전달해도 되도록** 작성했다.

관련 코드
- 모델 자산: `apps/shell/public/models/` (GLB 51개, 약 32MB), `apps/shell/public/maps/`
- 씬 정의: `apps/shell/public/scenes/*.json` (philly-2dock, 1dock, 2dock, goliath, dock-in)
- 씬 스키마: `packages/domain/src/3d/model/types.ts`, `packages/domain/src/3d/lib/sanitize-scene-info.ts`
- region → 씬 파일 매핑: `packages/domain/src/3d/model/scene-file-map.ts`
- 기존 최적화 파이프라인: `scripts/optimize-glb.mjs`, `scripts/optimize-map.mjs`
- 오프스크린 렌더(3단계에서 재활용 후보): `packages/widgets/src/3d/lib/offscreen-preview-renderer.ts`

## 보안 제약 (반드시 지킬 것)

이 프로젝트는 폐쇄망에 배포된다 (`docker save` → tar 반입 → 운영 서버 인터넷 없음.
`docker-compose.yml` 상단 주석 참조).

- **신규 npm 의존성 추가 금지.** `@gltf-transform/core` 는 이미 루트 devDependency 에
  있으므로 그것만 사용한다.
- 실행 중 **외부 네트워크 통신 금지.** 전부 로컬 파일 읽기로 완결되어야 한다.
- 결과물은 **숫자(JSON/Markdown)만.** 3D 모델 이미지·스크린샷을 생성하지 않는다 —
  실제 조선소 자산이라 아티팩트로 남으면 안 된다.
- 결과를 외부 서비스로 전송하지 않는다. 베이스라인은 리포지토리 안에 커밋해
  **git 히스토리를 성능 시계열 기록으로** 쓴다.

## 설계 원칙 (핵심)

지표를 두 종류로 **반드시 분리**한다. 섞으면 CI 노이즈에 게이트가 무너져서
아무도 보지 않게 된다.

| | 결정론 지표 | 시간 지표 |
|---|---|---|
| 예 | 삼각형 수, 프리미티브(드로우콜 하한), 재질·텍스처 수, 텍스처 VRAM 추정, 파일 바이트 | 프레임타임, 로드 시간 |
| 하드웨어 의존 | **없음** — 동일 입력이면 동일 값 | 큼 |
| 처리 | **절대 임계값으로 하드 실패** | 이번 범위 제외. 추가하더라도 절대 임계값 금지, base 대비 상대 비교만 |

## 작업 1 — 에셋 예산 (`scripts/perf-asset-budget.mjs`)

`apps/shell/public/{models,maps}` 의 GLB 를 `@gltf-transform/core` 로 파싱해
파일별로 산출한다.

- `bytes`, `triangles`, `primitives`(드로우콜 하한), `meshCount`
- `materials`, `textures`, `texturePixels`
- `vramEstimate` — 텍스처 픽셀 × 4바이트 × 1.33(밉맵).
  **압축 텍스처(KTX2/Basis) 여부를 구분해 표시할 것.**

`vramEstimate` 가 이 스크립트의 핵심 가치다. 파일 크기만 보면 안 보이는 항목이라
(압축 안 된 4K 텍스처는 파일 2MB인데 VRAM 80MB), 실제로 가장 자주 터지는 지점이다.

게이트 동작:
- `perf/budgets.json` 의 파일별 상한을 초과하면 종료코드 1
- **예산이 정의되지 않은 새 GLB 가 발견되면 실패**시킨다.
  이 조항이 없으면 게이트가 우회 가능해져서 무의미해진다.

## 작업 2 — 씬 정적 비용 (`scripts/perf-scene-cost.mjs`)

`apps/shell/public/scenes/*.json` 을 읽어 모델 인스턴스를 전개하고, 작업 1의 결과와
결합해 씬별 예상 비용을 산출한다.

- 인스턴스 수, 고유 모델 종류 수
- 합계 삼각형, 드로우콜 하한, 텍스처 VRAM(고유 텍스처는 중복 제거), 전송 바이트

씬 JSON 스키마는 `packages/domain/src/3d/model/types.ts` 의 `SavedSceneInfo` 와
`sanitize-scene-info.ts` 를 근거로 파악한다. **추측하지 말 것.**

이 단계의 효용: 씬 편집(오브젝트 추가·복제)이 성능에 미치는 영향이 PR diff 에
숫자로 드러난다.

## 작업 3 — 베이스라인과 리포트

- `pnpm perf` — 두 스크립트 실행 후 `perf/baseline.json` 과 비교, 사람이 읽을 표를 출력
- `pnpm perf:update` — 베이스라인 갱신. 의도된 증가를 커밋 기록으로 남기기 위한 명령
- 최초 실행 시 **현재 값을 그대로 캡처**해 베이스라인으로 삼고,
  **예산은 현재값 + 15% 여유**로 초기화한다. 임의의 이상적 수치를 넣지 말 것

출력 형태:

```
씬 philly-2dock        base      head        Δ       예산
드로우콜 하한            342       398     +16% ⚠️     400
삼각형                 4.2M      4.2M       0%      5.0M
텍스처 VRAM           210MB     210MB       0%     256MB
전송 바이트             18MB      18MB       0%      24MB
```

## 작업 4 — 모델 카탈로그 문서

`perf/model-catalog.md` 를 자동 생성한다. 모델별 삼각형·프리미티브·텍스처 VRAM 표.

목적은 게이트가 아니라 **예방**이다 — 씬 편집자가 모델을 배치하기 *전에* 비용을
볼 수 있게 한다. 사후 차단보다 이쪽이 효과가 크다.

## 3단계 — 실측 런타임 (후속, 보안 검토 필요)

이번 범위 밖이지만 설계 방향을 남긴다.

측정 전용 하네스 페이지(`/__perf?scene=...&view=...`)를 만들고 헤드리스 Chrome 으로
`gl.info.render.calls / triangles`, `gl.info.programs.length`, 프레임타임 p95 를 수집한다.

- `SceneReadyProbe`(`packages/features/src/3d/ui/scene-loading-overlay.tsx`)가 이미
  "모델이 실제로 마운트됨"을 정확히 알리므로, 타이머 추측 없이 측정 시작점을 잡을 수 있다
- 카메라 시점은 `use-scene-views-store` 의 북마크를 그대로 시나리오로 재사용한다
- `dpr` 을 1로 고정해야 한다 — 현재 기본값은 `[1, 1.5]`(`packages/ui/src/organisms/three-scene-viewer.tsx`)라 기기별로 달라진다
- `gl.info.programs.length` 는 특히 챙길 것. 셰이더 순열 폭발이 "첫 진입 멈춤"을 만드는데
  프레임타임 평균으로는 안 보인다

보안 관련 판단:
- 측정 자체는 localhost 정적 파일을 여는 것이라 외부 통신이 0이다.
  `--host-resolver-rules="MAP * ~NOTFOUND"` 로 외부 DNS 해석을 차단해 이를 기술적으로 보장할 수 있다
- 실제 장애물은 두 가지다 — **Chromium 바이너리 다운로드**(시스템 Chrome 을 `channel: 'chrome'`
  으로 붙이면 회피), 그리고 **외부 CI 러너**(소스와 조선소 3D 자산이 외부로 나감 → 사내 러너 또는 로컬 실행)
- 하네스 페이지에서 Google Maps 는 반드시 꺼둔다. 타일 요청이 나가면
  "측정 스크립트가 외부 통신을 한다"가 되어버린다
